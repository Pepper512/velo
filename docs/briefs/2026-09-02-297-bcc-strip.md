# SPEC-297 — The `Bcc` header must not leave the client over SMTP

- **Task:** Strip the `Bcc` header from the message bytes after the SMTP envelope has been built
  from it and before `send_raw` transmits them, so blind-copied recipients are not disclosed to
  every other recipient.
- **Tier:** **2** — the change is on the Rust SMTP send path (`CLAUDE.md` Part I: *Rust
  IMAP/SMTP/OAuth* is Tier 2), and a wrong strip either keeps leaking or breaks sending. Plan in
  the PR before code; threat pass and rollback below; both cross-vendor legs (ADR-004).
- **Base:** `main` @ `e6f3eb9` (code pin `9bec56a`). Every citation below was grepped at that pin.
- **Status:** building — branch `f297-bcc-strip`; Jim's instruction 2026-09-02 (*"start the
  bug-fix queue at #297"*), the build seat owns the PR and the merge.
- **Source:** upstream issue avihaymenahem/velo#297 (reported by a downstream reuser of the SMTP
  code); the fork's 2026-09-01 issue triage ranked it **P0** — the only privacy defect on the
  list. Bug-fix queue item 1 (`~/Vaults/Pepper Knowledge/10 Projects/Velo/Build Queue/10-Bug-Fixes/`).
- **Effort:** S · 1 build-day (the Rust half is ~40 lines; the tests and the fail-closed guard are
  most of it).

## Outcome

A message sent with blind-copied recipients through an IMAP/SMTP account reaches every recipient
without a `Bcc` header, while the blind recipients still receive it. The user's own copy in the
Sent folder keeps the `Bcc` line, as it does today, so they can see whom they blind-copied.

## The defect, verified in the fork

1. **The builder emits the header.** `buildRawEmail` (`src/utils/emailBuilder.ts:143-144`) writes
   `Bcc: …` into the raw RFC 5322 message whenever the draft has blind recipients. This is
   correct input for the SMTP layer: RFC 5322 §3.6.3 lets the submitting client use the field
   to build the envelope and requires it to remove the field before transmission.
2. **The SMTP client reads it into the envelope and then sends the bytes unchanged.**
   `extract_envelope` (`src-tauri/src/smtp/client.rs:88`) collects To, Cc **and Bcc**
   (`:127-135`) into the lettre envelope — right. `send_raw_email` (`:150`) then calls
   `transport.send_raw(&envelope, &raw_bytes)` (`:159`) with `raw_bytes` exactly as decoded.
   lettre's `send_raw` transmits the bytes it is given (lettre 0.11.23, `Cargo.lock`).
3. **The existing test cannot see it.** `test_extract_envelope_with_bcc` (`:231`) asserts the
   envelope has two recipients — true and desirable — and never looks at what is transmitted.
4. **The provider reuses the same bytes for the Sent copy.** `imapSmtpProvider.ts:455` sends
   `rawBase64Url`; `:474` appends the same string to the server's Sent folder; `:578` appends it
   to Drafts. Those copies are the user's own and *should* keep `Bcc`; only the wire copy must not.
5. **Gmail is out of the blast radius.** `gmailProvider` hands the raw message to the Gmail API,
   which owns Bcc handling on submission. Not touched, not tested here (assumption recorded
   below).

## Requirements

- **REQ-1** As a sender I want blind-copied recipients to stay blind so that a Bcc is what it says.
  - REQ-1.1 WHEN `send_raw_email` transmits a message THE SYSTEM SHALL transmit no `Bcc` header
    field, whatever the field name's case, whether the field is folded over several lines, and
    whether the message uses CRLF or bare LF line endings.
  - REQ-1.2 WHEN the message carries blind recipients THE SYSTEM SHALL still address the SMTP
    envelope to them (the current behaviour, now asserted against the transmitted bytes).
  - REQ-1.3 THE SYSTEM SHALL remove only header fields named `Bcc` from the header block: no
    other header (including ones whose name merely starts with `Bcc`) and nothing in the body
    is altered.
  - REQ-1.4 IF, after stripping, a full parse of the outgoing bytes still reports a `Bcc` field
    THE SYSTEM SHALL refuse to send and return an error naming the reason — fail closed, never
    "send and hope".
- **REQ-2** As a sender I want my own records unchanged.
  - REQ-2.1 THE SYSTEM SHALL leave the bytes appended to the Sent and Drafts folders, and the
    local sent-message record, exactly as today (with `Bcc`). The strip happens inside the Rust
    send command and nowhere else.

## Not doing

- Rebuilding outbound messages with lettre's typed `Message` builder (the issue's alternative).
  It would replace the whole TypeScript builder and its RFC 2047 / inline-image handling for a
  one-header problem — a different PR if ever.
- Stripping in `emailBuilder.ts`. The builder's output is also the Sent/Drafts copy (REQ-2.1),
  and the wire is Rust's responsibility.
- Any change to the Gmail path.
- Header-encoding and escaping (#293 upstream) — different defect, no overlap.

## Design

- **Change** — `smtp/client.rs` gains `strip_bcc_header(raw: &[u8]) -> Vec<u8>` and
  `prepare_for_wire(raw) -> Result<(Envelope, Vec<u8>), String>`. `prepare_for_wire` calls the
  existing `extract_envelope` on the original bytes (so Bcc reaches the envelope), strips, then
  re-parses the stripped bytes with `mail_parser` and returns `Err` if `bcc()` is still `Some`
  (REQ-1.4). `send_raw_email` uses it; nothing else changes.
- **The scanner** works on the header block only — everything before the first empty line
  (`\r\n\r\n` or `\n\n`), or the whole input when there is none. A header line whose field name
  is `bcc` (ASCII case-insensitive), optionally followed by whitespace before the colon (RFC 5322
  §4.5.3 obsolete syntax, which `mail_parser` accepts and which must therefore be stripped too),
  is dropped together with every continuation line that follows it (lines starting with SP or
  HTAB). All other lines are copied byte for byte. The body is copied untouched.
- **Decision & alternatives.** (a) Use `mail_parser`'s header byte offsets from the parse that
  `extract_envelope` already does — avoids a second scan, but ties the strip to a crate whose
  offset semantics are version-specific and which PR E is about to bump (0.9 → 0.11). (b) A
  hand-written header-block scanner — thirty lines, fully unit-testable, parser-independent.
  **(b), with (a)'s parser as the fail-closed check** rather than the mechanism: the guard
  catches any `Bcc` spelling the scanner misses but the parser recognises, and turns it into a
  refusal instead of a leak.
- **Data / schema** — none.
- **Failure modes** — strips too little → REQ-1.4 refuses the send with an error the user sees;
  the message is not lost (the composer still holds it). Strips too much → only a field literally
  named `Bcc` in the header block can be removed, so the worst case is a message with no `Bcc`
  line, which is the intended wire form. A header block with no terminating blank line is
  treated as all-headers, which is what a parser would do.

## Threat pass (Tier 2)
- **Asset:** the identities of blind-copied recipients.
- **Entry points:** the composer (user input), `mailto:` deep links (header injection already
  closed by audit P7 — `sanitizeHeaderValue`, `emailBuilder.ts:113`), drafts restored from the
  server.
- **What an attacker gains today:** nothing they have to do — every recipient of any Bcc'd
  message from an IMAP/SMTP account already sees the blind list. This change removes a
  disclosure; it adds no new capability.
- **Mitigations in this change:** the strip is bounded to the header block and to fields named
  `Bcc`; the fail-closed re-parse guard (REQ-1.4) means any spelling the scanner misses becomes a
  refused send, not a leak; the body — attacker-influenceable via quoted content — is never
  edited, so a body line `Bcc: …` cannot be used to make the scanner cut into the message.
- **Residual:** `mail_parser` and the scanner could both miss a spelling; that is the same
  exposure lettre-based clients that strip via a parser carry, and it is bounded by RFC 5322's
  grammar for the field name. Gmail path unverified here — **ASSUMPTION:** the Gmail API strips
  `Bcc` on submission (documented behaviour); not tested in this PR.
