## What part 2 adds, in dependency order

1. **Pass id and attestation** (`imapDeltaSync`, spec REQ-1.2b). Generate `passId = crypto.randomUUID()`
   **once** at the top of the pass and use it for every folder (a fresh id per call would let one
   search reported twice promote on the second call — Grok Q3 on #44). Attestation is computed at
   the *end*, from **two** per-folder bits: `deltaResultMap.get(f.raw_path)?.checked === true`
   (the delta check produced an observation — a missing map entry counts as unchecked) **and**,
   for every folder the gate opened, `searchAllSucceeded.has(f.raw_path)` (the `imapSearchAllUids`
   call returned, i.e. `applySearchAll` ran). `DeltaCheckResult.checked` alone is *not* "a
   `UID SEARCH ALL` ran" — the UIDVALIDITY-changed row is `checked` with no search (Grok M2).
   `attested = listSucceeded && syncableFolders.every(both bits) && newFoldersAllSucceeded`.
   **Concurrency (plan read, NIT 8):** `syncManager.runSync` holds one `syncPromise` for the whole
   process and queues any sync requested while it runs, so two delta passes for one account never
   overlap and two pass ids never observe the same folder within milliseconds. The one bypass is
   `ImapSmtpProvider.deltaSync`, which calls `imapDeltaSync` directly; it is not used by the
   background scheduler. Verified 2026-09-02.
   A thrown `imapListFolders` (or a partial LIST — treat any error as partial) sets
   `listSucceeded = false`. The circuit breaker needs no change: its failures already push to
   `deltaFolderErrors` and leave folders unchecked. **Evaluate against the syncable-folder set,
   never against `deltaResultMap.values()`** (Gemini Q2 on #44).
2. **The gate** (REQ-2.1) — per existing folder, after the delta result is known and before
   fetching new UIDs: `shouldListAll = deltaResult.exists !== localCount + state.flagged_not_expunged`,
   where `localCount = SELECT COUNT(*) FROM messages WHERE account_id AND imap_folder = folder AND moved_to IS NULL`
   (**tombstones excluded from the count** — they are already known-moved; carried from the Grok
   review of #43, H2-A, recorded in the vault spec's Not-doing). `flagged_not_expunged` is read from
   `folder_sync_state` (part 1 added the column; add `getFolderSyncState` → typed field and a small
   `incrementFlaggedNotExpunged(accountId, folder, n)` in `db/folderSyncState.ts`).
3. **The full list** — when the gate fires (and only for `checked` folders whose `exists` is
   non-null; a UIDVALIDITY-changed folder takes the full-resync path and skips the gate):
   `serverUids = await withSession(.., (id) => imapSearchAllUids(id, folder))` (validated at the
   boundary in part 1; a throw is a folder error → not in `searchAllSucceeded`, *not* an empty
   list). Then **one call**: `applySearchAll({ accountId, folder, uidvalidity: deltaResult.uidvalidity, passId, presentUids: serverUids, missing: diffVanished(localUids, serverUids).map(uid => ({uid, messageRowId})) })`
   — it purges other generations, clears reappeared UIDs and records the missing ones in one
   transaction (the trio is a hard invariant; Grok M4). `localUids` are the folder's live rows
   (`moved_to IS NULL`); tombstoned rows whose UID is absent are **deleted directly**
   (already-moved; see 2). Then **recompute** the counter
   (REQ-2.2): `flagged_not_expunged := |serverUids − localUids|` — only if this folder's new-message
   fetch also completes this pass (rev 5's both-steps clause); otherwise leave it.
4. **The counter's increments** (REQ-2.2) — where `noticeIfNotExpunged` already receives a
   `RemovalResult { expunged: false }` in `imapSmtpProvider` (`archive`/`trash`/`spam`/
   `moveToFolder`/`permanentDelete`), add `incrementFlaggedNotExpunged(accountId, sourceFolder, uids.length)`.
   Note the F-5 interaction: on a move with `expunged: false` the source rows are *tombstoned*, so
   they leave the local count in 2 but the server still lists them — which is exactly what the
   counter is for. The two agree by construction.
5. **REQ-2.3 belt** — on accounts with `has_uidplus == false` known (the `warn_uidplus_missing_once`
   log is the only signal today; add a `folder_sync_state`-level or account-level flag set from
   `RemovalResult { expunged: false }`), a persistent gate mismatch after a list fetch falls back to
   `UID SEARCH NOT DELETED` count once per 10 passes. **Needs one Rust command**
   (`imap_count_not_deleted`), thin over `session.uid_search("NOT DELETED")`. Do this last; it is
   the least valuable piece and the only new wire surface.
6. **End-of-pass deletion** (REQ-1.2, REQ-1.3, REQ-3.1–3.4) — only if `attested`. Per folder:
   `confirmed = await confirmedOnPass(acct, folder, uidvalidity, passId)`; skip rows whose message or thread has
   `pending_operations` (REQ-3.4; query `pending_operations.resource_id = thread_id` — see
   `db/pendingOperations.ts`); `plan = planDeletions(localRows, confirmed.length)`; if `plan.stop`
   → log, raise the REQ-3.1 confirmation (step 8) and delete nothing; else delete the first
   `plan.budget` rows (oldest first — `confirmedOnPass` already orders): `deleteMessage` +
   `forgetSuspects`, and delete the thread + its labels only if the thread has no other messages
   (REQ-1.3; there is no helper for "thread has other messages" — add `threadMessageCount` to
   `db/threads.ts`). Log each deletion at `info` with folder, UID, Message-ID (REQ-3.2). All inside
   `withTransaction`.
7. **REQ-4 reconcile op** — `queueProcessor`: on a `VELO_OUTCOME_UNKNOWN:` error from a move/delete,
   enqueue `{ operation_type: "reconcile", resource_id: "reconcile:{folder}", params: { folder, uids } }`.
   `compactQueue` (`db/pendingOperations.ts:147`) gains a branch: newest-per-folder with merged UID
   sets, `retry_count = max`, only `status = 'pending'` rows. Handler: targeted `UID SEARCH <set>`
   (**one more thin Rust command**, `imap_search_uids_present`, over `uid_search(&set)` with
   `wire::validate_uid_set`); absent → `recordMissing` as suspect; present → notice + remove op.
   3 strikes → mark the folder for a full-list pass (a `folder_sync_state.force_list INTEGER`
   column — **migration 27**, paired) + notice (REQ-4.3). Queue UI labels it a repair (REQ-4.4).
   User ops drain first (REQ-4.5).
8. **The REQ-3.1 stop UI** (spec Task 12) — mount `ConfirmDialog` (`components/ui/ConfirmDialog.tsx`,
   tested, currently unmounted) from the sync layer via a store flag: `useUIStore.reconcileStop =
   { accountId, folder, confirmed, localRows }`; the dialog offers *Delete them* (runs step 6 with
   the stop bypassed for that folder, still under the cap per pass) or *Full resync* (existing
   UIDVALIDITY-changed path). Until answered, the folder stays frozen and the notice repeats once
   per pass at most.

## Threat pass (Tier 2)

The server's UID list drives local deletions — through two confirmed observations on attested
passes, under a binding cap, with a hard stop behind a human above 50%, with logging. A hostile
"everything vanished" answer: pass 1 records; pass 2 needs attestation and a real search; deletes at
most `cap` rows per pass; above 50% deletes nothing. A partial or malformed list is a thrown boundary
error, not an empty list. The targeted `reconcile` UID set passes `wire::validate_uid_set` before the
wire. No credential is touched.

# Part 3 — the follow-up (plan, 2026-09-02, before code)

Three pieces, one PR, Tier 2 (Rust wire surface + a path that removes sync state). Nothing in it
deletes a message row.

## A. REQ-2.3 belt — `UID SEARCH NOT DELETED` once every N passes
- **Rust:** `count_not_deleted(session, folder) -> u32` (SELECT + `UID SEARCH NOT DELETED`, count
  only) and the command `imap_count_not_deleted`. TS wrapper validates a non-negative integer.
- **Clock:** `folder_sync_state.reconcile_passes` (migration 27) is bumped once per delta pass per
  existing folder; N = 10.
- **When:** the folder shows the no-UIDPLUS signature — `flagged_not_expunged > 0` — **and** the
  gate would open. On passes where `reconcile_passes % 10 === 0` the belt runs *instead of* the full
  list: `notDeleted = imapCountNotDeleted(folder)`; the counter is recomputed as
  `exists − notDeleted` (clamped ≥ 0); if `notDeleted === live + incomingNewUids` nothing vanished
  and the folder is treated as gate-closed (no list, no suspects aged). Otherwise the full list runs
  as before. On every other pass the gate behaves exactly as in part 2. A belt error is a folder
  error (unattested pass), never an empty observation.
- **Why not always:** the belt cannot tell *which* UIDs vanished, so it cannot age suspects; it only
  saves the list when nothing did.

## B. REQ-4 reconcile op — a targeted check after an unknown outcome
- **Enqueue** (REQ-4.1): in `executeEmailAction`, when the provider throws a `VELO_OUTCOME_UNKNOWN:`
  error for `archive`/`trash`/`spam`/`moveToFolder`/`permanentDelete`, enqueue
  `{ operation_type: "reconcile", resource_id: "reconcile:{folder}", params: { folder, uids } }` per
  source folder (folder/UIDs parsed from the ids), `max_retries: 3`. The existing
  `noticeIfNotExpunged` path is untouched (interleaves, does not replace).
- **Rust:** `search_uids_present(session, folder, uid_set) -> Vec<u32>` (`UID SEARCH UID <set>`,
  `wire::validate_uid_set` before the wire) and `imap_search_uids_present`. TS wrapper validates
  the answer is a subset of what was asked.
- **Handler** (REQ-4.5): `executeQueuedAction` routes `reconcile` to `runReconcileOp`: fresh
  session, `present = imapSearchUidsPresent(folder, uids)`; **absent** UIDs → `recordMissing` as
  suspects under a pass id `reconcile:<uuid>` (the queue never deletes; the next two delta passes
  do the confirming); **present** UIDs → the operation did not take effect: notice *"N message(s)
  in {folder} were not moved/deleted — the server still has them"* and the op completes. A UID with
  no local row is ignored.
- **Compaction** (REQ-4.2): `compactQueue` gains a branch for `reconcile` ops sharing a resource:
  keep the newest, merge the UID sets into it, `retry_count = max`, delete the rest — pending rows
  only (`compactQueue` already reads only `status = 'pending'`).
- **Degrade** (REQ-4.3): when the queue processor marks a `reconcile` op failed (non-retryable, or
  retries exhausted — `max_retries` 3), it sets `force_list = 1` on the folder's sync state and
  raises a notice. The next delta pass lists that folder regardless of the gate and clears the flag.
- **Priority** (REQ-4.5): `getPendingOperations` orders `reconcile` ops after user ops within a
  batch (`ORDER BY (operation_type = 'reconcile'), created_at`).
- **Label** (REQ-4.4): the queue surface is a count badge and a Settings line, not a per-op list;
  the op's `params` carry `kind: "repair"` so any future list can label it. Recorded, nothing to
  render today.

## C. The "folder gone" path
- After a successful LIST, every folder with sync state that the LIST did not return gets
  `missing_passes + 1` (migration 27); a folder the LIST did return gets it reset to 0.
- On the **second consecutive** miss the folder is taken as gone on the server: its
  `folder_sync_state` row is deleted (attestation resumes), its suspects and any stop for it are
  invalidated, and a notice says *"{folder} no longer exists on the server; its N cached messages
  are kept"*. **Its message rows are not deleted** — that would be a mass removal on LIST
  evidence alone, which REQ-1 forbids; the user can delete the label.
- While `missing_passes` is 1 the folder is unchecked, so that pass does not attest — one pass of
  no deletions, the same price a vanished UID pays.
- A folder the user actually deleted through Velo already loses its sync state through the
  existing delete path, so it never enters this.

## Tests (harness unless noted)
- Belt: runs only on the Nth pass with the no-UIDPLUS signature; recomputes the counter; skips the
  list when counts agree; lists when they do not; a belt error unattests.
- Reconcile op: enqueued per folder on an unknown-outcome error with `max_retries` 3 (unit, mocked
  provider); handler records absent UIDs as suspects (harness) and notices on present ones; never
  deletes; compaction merges UID sets and keeps max attempts; degrade sets `force_list`; the next
  pass honours and clears `force_list` (sync wiring test); reconcile ops sort after user ops.
- Folder gone: first miss → unchecked, unattested, row kept; second miss → row removed, notice,
  messages kept, attestation resumes; reappearance resets the count.
- Rust: `search_uids_present` rejects a bad set before the wire (unit); both commands registered.
- Live Dovecot (Done-when, by hand): the part-2 scenarios plus a reconcile op against `:11143`
  (move that "timed out" → op → suspect → two passes → gone) — transcript on the PR.
