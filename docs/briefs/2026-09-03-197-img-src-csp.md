# SPEC-197 — Remote images never load: the CSP `img-src` blocks what the opt-in allows

- **Task:** Let a remote image load once the user has allowed it (globally, by turning "Block
  Remote Images" off, or per sender via the allowlist) by widening the webview CSP's `img-src`
  to `https:` — the decision Jim made on 2026-09-02 (widen behind the opt-in; the Rust proxy is
  queued as a later privacy enhancement).

  before code; threat pass and rollback below; both cross-vendor legs (ADR-004).
- **Base:** `main` @ `497955b` (code pin `848ccaa`). Every citation below was grepped at that pin.
- **Status:** building — branch `f197-img-src`; Jim's decision 1 of 2026-09-02 and his

- **Source:** upstream avihaymenahem/velo#197 (images stay broken with "Block Remote Images"

  item 6.
- **Effort:** XS · ¼ day.

## Outcome

With "Block Remote Images" off, or a sender allowlisted, an email's remote images load. With
the block on (the default) nothing changes: the sanitizer still strips every remote `src` and
no request leaves the app.

## The defect, verified in the fork

1. **The block is enforced by the sanitizer, not the CSP.** `EmailRenderer.tsx:42`
   `shouldBlock = blockImages && !senderAllowlisted && !overrideShow`; when it is true the HTML
   goes through `stripRemoteImages` (`:64-81`), which moves `src` to `data-blocked-src`
   (`sanitize.ts:19` lists that attribute). When it is false the sanitized HTML keeps `src`.
2. **The CSP then blocks the load.** The email body is written into a same-origin iframe
   (`EmailRenderer.tsx:119-126`, `sandbox="allow-same-origin"`, `:241`), which inherits the
   window's CSP. `tauri.conf.json:42`: `img-src 'self' data: https://www.gravatar.com
   https://lh3.googleusercontent.com https://*.googleusercontent.com` — Gravatar and Google
   avatars only. Any other host is refused by the webview before a request is made: the
   reporter's "images remain broken despite the setting being off".
3. So the opt-in does exactly what it says up to the sanitizer and is silently overruled one
   layer down.

## Requirements

- **REQ-1** As a user who allowed remote images I want them to load.
  - REQ-1.1 THE SYSTEM SHALL allow `https:` sources in `img-src` (keeping `'self'` and `data:`).
  - REQ-1.2 THE SYSTEM SHALL NOT allow `http:` image sources — a plaintext fetch from inside
    the mail client would leak the reader's IP and the mail's identity in the clear; Jim's
    decision names `https:`.
  - REQ-1.3 A test SHALL pin the `img-src` directive: contains `https:`, `'self'`, `data:`; does
    not contain `http:`, `*`, or `'unsafe-inline'`; and the other directives are unchanged
    (`connect-src`, `script-src` … exact).
- **REQ-2** As a user who did not opt in I want no request to leave.
  - REQ-2.1 The default (`block_remote_images` = true) and the sanitizer's stripping are
    untouched; the existing tests for `stripRemoteImages` / `hasBlockedImages` stay green.

## Not doing

- A Rust image proxy (queued: strips the reader's IP and headers from tracking pixels; a
  privacy enhancement, not this bug).
- `http:` images (REQ-1.2).
- Changing the sandbox flags. The sanitizer is unchanged **except** for one blocker addition
  found in review (Gemini H1 on #60): `href` on SVG `<image>`/`<use>` fetches on render and was
  not in the blocker's fetching-attribute list — the four-host CSP had been masking it.
  `stripRemoteImages` now removes a remote `href` on every element that is not a link. The
  audit-P9 design (neutralise every fetching attribute, DOM-based) is what made the gap a
  one-line fix rather than a new mechanism.

## Design

- One directive edit in `tauri.conf.json`: `img-src 'self' data: https:`. The three explicit
  hosts are subsumed by `https:` and dropped, so the directive reads as the policy it is.
- `src/config/tauriConfig.test.ts` gains a CSP test parsing the directive list.
- **Decision & alternatives.** (a) Widen `img-src https:` — Jim's decision; the opt-in stays
  the sanitizer's. (b) Per-request proxy through Rust — later. (c) Keep the CSP and rewrite
  `src` to a `data:` URL fetched by Rust — the proxy by another name.
- **Failure modes** — none new for blocked mail (no `src` remains). For allowed mail the
  browser now fetches what the user allowed: the tracking-pixel exposure that "Block Remote
  Images" exists to prevent, which the user turned off knowingly.

## Threat pass (Tier 2)
- **Asset:** the reader's network identity (what a remote image request discloses) and the
  webview's script/connect boundaries.
- **Entry points:** email HTML (attacker-controlled) → sanitizer → iframe.
- **What an attacker gains:** with the block off or the sender allowlisted, an image request to
  any HTTPS host — which is the feature the user opted into. Nothing beyond images: `script-src`,
  `connect-src`, `frame-src` are unchanged and pinned by the test; the sandbox stays.
- **Mitigations in this change:** `https:` only; a test that fails if any other directive moves.
- **Residual:** tracking pixels for opted-in users — the accepted cost until the proxy. Also
  (Grok L4 on #60): an opted-in image GET may target any HTTPS host, including the OAuth and
  Graph hosts in `connect-src`; Velo's OAuth completes in the system browser with a localhost
  redirect and the webview authenticates APIs with bearer headers, so the webview's cookie jar
  holds no provider session, but the request itself is what the opt-in permits. `http:` and
  `blob:` stay out of `img-src` and the test asserts both.
- **Verified in review:** the blocker's coverage — every fetching attribute, inline-style
  URLs, and now SVG `href` — is what the threat pass rests on, not "no `src` remains".
