# ADR-001 — `better-sqlite3` as the real-SQLite test harness

- **Status:** Accepted
- **Date:** 2026-09-01
- **Decider:** Jim

## Question

Every DB module is tested against mocks: 53 of 133 test files mock
`services/db/*`, and no SQL string, FTS5 query, trigger, or migration is ever
executed by the suite (audit P6, P8, P12). The production DB is SQLite via
`tauri-plugin-sql`, which only exists inside a Tauri runtime. Tests need a
SQLite that runs under Node/Vitest.

## Decision

Add **`better-sqlite3`** as a **devDependency** only. It is never bundled into
the app. Types are a hand-written `src/test/better-sqlite3.d.ts` — no
`@types/better-sqlite3`.

Not covered: how migrations are executed against it (that harness is designed
in the Batch B brief for P6), and whether production ever moves off
`tauri-plugin-sql` (no).

## Options

| Option | Strongest case for | Strongest case against | Verdict |
|---|---|---|---|
| `better-sqlite3` (native) | Same SQLite engine semantics incl. FTS5 + trigram; synchronous API is ideal for tests; mature, widely used | Native build on each CI runner (adds ~20 s; prebuilt binaries cover Node 22 on ubuntu/macos/windows) | **Chosen** |
| `sql.js` (WASM) | No native build | Slower; separate WASM SQLite build whose FTS5 availability must be verified per release; async loading complicates harness | Rejected |
| `node:sqlite` (Node ≥ 22.5 built-in) | Zero dependency — matches the "prefer stdlib" rule | Still marked experimental at time of decision; FTS5/trigram availability depends on Node's bundled SQLite build; flag-gated on some versions | Rejected for now — **revisit** when stable |
| Keep mocking | No dep | Leaves migrations and search unverifiable; the exact gap the audit ranked #1 in tests | Rejected |

## Recorded dissent & tripwire

A test-only native module is still a native module compiled from a lockfile
on every runner. Accepted because it is dev-scoped, has prebuilt binaries for
all three CI platforms, and buys the single largest test-coverage gap.

**Revisit if:** `node:sqlite` stabilizes with FTS5 + trigram on Node 22 LTS —
then remove this dependency (exit path below). Or if the native build breaks
on a required CI platform twice.

## Consequences

- `src/test/sqliteHarness.test.ts` smoke-tests load, FTS5, and trigram on
  every CI run; a failing smoke test means the harness, not the app, broke.
- Batch B/C may now write tests that execute real SQL (`runMigrations`,
  `buildSearchQuery`, `pendingOperations`).
- `Cargo`/Tauri unaffected.

---

## Dependency block

- **Package / version:** `better-sqlite3` `^13.0.3` (latest at 2026-09-01; see `package-lock.json` for the exact pin), devDependencies only.
- **Replaces:** nothing in production. Replaces ~90 `vi.mock("…/db/…")` stubs over time in tests.
- **Maintenance:** maintainer WiseLibs (Joshua Wise); long-lived (since 2016), frequent releases tracking SQLite; post-1.0 for years.
- **Blast radius:** dev/test only; not in the bundle; if it dies, tests revert to mocks — app unaffected. Transitive deps: `bindings`, `prebuild-install` (downloads a prebuilt binary or compiles with node-gyp). Network access at install time (prebuilt fetch) — from the lockfile-pinned version.
- **Exit path:** delete the devDependency and `src/test/better-sqlite3.d.ts`; swap harness to `node:sqlite` behind the same tiny surface (`exec`, `prepare().run/get/all`, `close`).
