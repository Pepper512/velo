# ADR-002 — Error-handling policy for failure paths

- **Status:** Accepted
- **Date:** 2026-09-01
- **Decider:** Jim (Batch C, audit P14)

## Question

79 of 218 `catch` bodies in non-test TypeScript are console-only, and there are
20 no-op `.catch(() => {})`. The audit's framing is the right one: these produce
**"the user believes X happened and it didn't"** bugs, which are the most
expensive class in a mail client — the user acts on a false belief (closes the
composer, trusts that a message is in Sent, assumes a folder is syncing) and the
data is gone by the time anyone notices.

A blanket rule ("never swallow an error") is not useful: some failures genuinely
are best-effort, and converting all 79 at once would be a large untested diff
through every service.

## Decision

Every `catch` in this codebase belongs to exactly one of three buckets, and the
bucket determines the handling.

### 1. Propagate — the caller cannot proceed correctly without knowing

Throw a typed error. The caller decides.

Use when the operation's result is a precondition for what follows: credential
decryption (`CredentialDecryptError`, Batch B), migration failure, a parse whose
output is then used.

### 2. Surface — the user's mental model is now wrong

Put it in the UI, next to the thing the user believes succeeded. Not a toast
that disappears; state that persists until the situation changes.

Use when the user would otherwise act on a false belief:

- **draft auto-save failed** while they are still typing → the composer's
  save-state label must say so (implemented in this batch)
- **credential decryption failed** → re-auth banner (Batch B)
- **a message was sent but not filed to Sent** → the message is not lost, but
  "it's in my Sent folder" is false
- **a folder has stopped syncing** → "I have all my mail" is false

### 3. Log — nothing downstream depends on it and no belief is affected

`console.error` with enough context to debug, and move on. This is a legitimate
bucket, not a failure of nerve.

Use for: best-effort caches, telemetry, cosmetic refreshes, a background flush
that will be retried on its own schedule anyway.

## Scope of this batch

Applied to the sites the audit named, **not** swept across all 79. New code is
expected to follow the policy; existing sites move as their area is touched.

## Correction to the audit

The audit states of `queueProcessor.ts:38` that a malformed `op.params` causes
`JSON.parse` to throw and be "possibly retried forever every 30 s; no retry
ceiling after `incrementRetry:49`". **Both halves are wrong**, verified in the
code and now pinned by tests:

1. `classifyError` (`src/utils/networkErrors.ts:80`) returns
   `{ type: "permanent", isRetryable: false }` as its **default**. A JSON
   `SyntaxError` matches no auth, quota, server or network pattern, so it takes
   that branch and the operation is marked `failed` on the **first** attempt.
2. `incrementRetry` (`src/services/db/pendingOperations.ts:86`) **does** have a
   ceiling: at `retry_count >= max_retries` it sets `status = 'failed'`.

So the poison-message path already dead-letters. Tests were added to keep it
that way rather than "fixing" something that works. This is the fifth audit
claim to fail verification — see `LOG.md` for the running list.

## Consequences

- The three buckets give reviewers a question with a right answer ("which bucket
  is this, and does the handling match?") instead of a judgment call.
- Bucket 2 requires a UI surface, so it is the expensive one. That is deliberate:
  it should cost something to decide the user needs to know.
- No lint rule enforces this yet. `no-floating-promises` would catch a related
  class and is worth adding when a linter decision is made (deferred, per the
  audit's "Biome / pnpm / TS linter are separate dependency decisions").
