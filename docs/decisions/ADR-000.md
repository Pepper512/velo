# ADR-000 — Stack

- **Status:** Accepted (amended 2026-09-01 — see Amendments)
- **Date:** 2026-09-01
- **Decider:** Jim

## Question

Every project's first ADR pins its languages, frameworks, and services
(`docs/methodology/06-decisions.md`). This workspace exists to build on
**Velo** — an existing, open-source (Apache-2.0) local-first desktop email
client cloned at `velo/` from `https://github.com/avihaymenahem/velo.git`
(v0.4.21, HEAD `ec47a7a`). Its stack is already chosen and shipped to
users on macOS, Windows, and Linux. Jim's recurring default
(`~/claude-memory/STACK-DEFAULTS.md`: Hono · tRPC · Postgres/Drizzle/RLS ·
Better Auth · Turborepo/pnpm) is a **server-backed multi-tenant web** stack
and does not describe this codebase. The question is therefore not "which
stack?" but "pin the inherited stack honestly, and name where Jim's
standard still applies to it."

## Decision

Adopt Velo's existing stack as this project's stack, exactly as found in
`velo/package.json`, `velo/src-tauri/Cargo.toml`, `velo/tsconfig.json`, and
`velo/src-tauri/tauri.conf.json` on the date above. **Do not migrate toward
the web default.** Jim's process and security rules apply in full; the
stack-specific rules translate as recorded in "Standard → this stack"
below.

This ADR does **not** cover: the `landing/` marketing site (separate npm
package, out of scope until someone works on it); whether Velo-Build
becomes a fork, a contributor branch, or a vendored copy (separate
decision, pending); adding *any* new dependency (each needs its own
dependency block, `06-decisions.md`).

## Stack as inherited

| Layer | Choice (pinned as found) |
|---|---|

| Native layer | Rust, edition 2021, MSRV 1.77.2, crate `app_lib` |
| Async runtime | tokio 1 (`net`, `io-util`, `sync`, `macros`, `rt`, `time`) |
| IMAP | `async-imap` 0.10 + `tokio-native-tls` + `mail-parser` 0.9 + `utf7-imap` |

### Data

| Layer | Choice (pinned as found) |
|---|---|
| Database | SQLite via `tauri-plugin-sql` (`sqlite:velo.db` in `$APPDATA`) |
| Schema | 19 hand-written migrations, 35 tables, FTS5 trigram full-text index (no ORM) |
| Tenancy | **Single-user, single-device.** No RLS; the tenant boundary is the OS user account. |
| Secrets at rest | Gmail OAuth tokens and IMAP/SMTP passwords: AES-256-GCM (WebCrypto) with a random 256-bit key generated on first launch and stored in `$APPDATA/velo.key` **beside the database** — not in the OS keychain. AI API keys: SQLite `settings` table. |

### Identity & external services

| Concern | Choice (pinned as found) |
|---|---|
| Gmail / Google Calendar | OAuth 2.0 + PKCE; loopback server in Rust on `127.0.0.1:17248`; user supplies their own Client ID; no client secret |
| IMAP/SMTP | Password / app-password; TLS, STARTTLS, or plain; XOAUTH2 supported |
| Contacts avatars | Gravatar (HTTPS) |
| AI providers | Anthropic (`@anthropic-ai/sdk` 0.74), OpenAI (`openai` 6), Google Gemini (`@google/generative-ai` 0.24) — called **directly from the webview** with user-supplied keys; CSP also permits local Ollama/LM Studio (`localhost:11434`, `:1234`) and `models.github.ai` |
| Backend servers | **None.** No Velo-operated service, no telemetry. |

### Testing, quality, release

| Concern | Choice (pinned as found) |
|---|---|
| Unit/component tests | Vitest 4 + Testing Library + jsdom, colocated `*.test.ts(x)` — **matches default** |
| E2E | none |
| Lint / format | **none configured** (no Biome/ESLint/Prettier) |
| Rust checks | none in CI (`cargo clippy`/`cargo audit` not wired) |
| CI | GitHub Actions: `release-please`, `release` (runs `npm run test` then `tauri build` per OS), `packaging` (RPM/Flatpak), `update-homebrew` |
| Distribution | Tauri bundler → `.dmg`/`.app`, `.msi`/`.exe`, `.deb`/`.AppImage`/RPM/Flatpak; Homebrew tap; auto-update via `tauri-plugin-updater` with a **minisign public key** pinned in `tauri.conf.json`, manifest from GitHub Releases |
| Versioning | release-please (conventional commits), `x-release-please-version` in Cargo.toml |

### Security posture as shipped (`velo/SECURITY.md`, `tauri.conf.json`, `capabilities/default.json`)

- CSP: `default-src 'self'; script-src 'self'`; `connect-src` allowlisted to
  Google, Anthropic, OpenAI, Gemini, Gravatar, Microsoft, Yahoo, GitHub
  Models, and local LLM ports; `frame-src 'self'`.
- Tauri capabilities: one `default` capability for windows `main`,
  `splashscreen`, `thread-*`, `compose-*`. `fs` scoped to `$APPDATA/**`.
  **`http:default` allows `http://*` and `https://*`** — broad; CSP is the
  effective network control, not the plugin scope.
- Phishing heuristics (10 rules) and SPF/DKIM/DMARC badges in the reading
  pane.
- Vulnerability reporting: `security@velomail.app` / GitHub private
  advisory; 90-day coordinated disclosure.

## Standard → this stack

How Jim's hard rules map onto a local-first desktop app. This is the
binding interpretation until an ADR changes it.

| Jim's rule | Applies here as |
|---|---|
| TypeScript strict, `noUncheckedIndexedAccess`, no `any` | Already satisfied by `tsconfig.json`. Keep it. Rust side: `#![deny(warnings)]`-equivalent via clippy once CI is wired. |
| Validate all input with Zod at every boundary | **Zod is not in the project.** The boundaries are: (1) Tauri IPC `invoke()` results and Rust command arguments, (2) IMAP/SMTP/Gmail/CalDAV responses, (3) **LLM output** (categorization, task extraction, auto-drafts, Ask Inbox), (4) `mailto:` deep-link args, (5) email HTML/headers. Rule stands; **adding Zod requires Jim's approval + dependency block** — until then, boundary validation is hand-written and type-narrowed, never `as`-cast. |
| LLM output is untrusted input | Directly applicable and higher-stakes than usual: model output must never reach SQL (`db/`), the filesystem (`fs` plugin), `invoke()`, or the composer's send path without validation. Prompt injection via email body → AI features is the primary threat. |
| Authz in the handler, never middleware-only | No HTTP handlers. Equivalent: every Rust `#[tauri::command]` validates its own arguments and never trusts the webview; Tauri capabilities are the "middleware" and must not be the only check. |
| Postgres RLS as tenant backstop | **N/A** — single-user SQLite. Tenant isolation is the OS user boundary. Record as N/A in every handoff, not as satisfied. |
| Never hardcode secrets; runtime secret manager; Zod-validated env | No server env to validate. Secrets are user-supplied at runtime. Standard says the secret store should be the platform's: **OS keychain (macOS Keychain / Windows Credential Manager / libsecret) rather than `velo.key` on disk.** Not changed by this ADR — see tripwire. The updater minisign pubkey in `tauri.conf.json` is public by design and is not a secret. |
| Ask before adding ANY dependency | Applies to `package.json`, `Cargo.toml`, and Tauri plugins alike. Cargo features count. |
| CI is the only source of test status | Upstream CI runs tests only in the release workflow. Until PR CI exists, **no agent may report a green gate** — only "ran locally, observed X." `EXCEPTIONS.md` already records this. |
| Small focused functions; deterministic first, AI second | Velo's `categorization/` (rules) → `ai/` (fallback) already follows this. Preserve the ordering. |

## Options

| Option | Strongest case for | Strongest case against | Verdict |
|---|---|---|---|
| Pin the inherited Tauri/Rust/React/SQLite stack as-is | It's what ships; zero migration risk; upstream-compatible contributions stay possible | Diverges from Jim's default in ORM, auth, tenancy, package manager, linting | **Chosen** |
| Adopt Jim's web default verbatim (previous ADR-000 text) | Consistency across Jim's projects | Describes software that doesn't exist here; every PR would be a "deviation"; would make the ADR a lie | Rejected |
| Pin inherited stack *and* immediately add Zod + Biome + pnpm to close the gaps | Fastest route to standard-compliant tooling | Three dependency decisions bundled into a stack ADR, without Jim's per-dep approval; pnpm switch breaks upstream's lockfile and CI | Rejected — each is its own dependency block, proposed separately |

## Recorded dissent & tripwire

**Dissent:** Pinning what we found means pinning three things Jim's
standard would not choose: an on-disk encryption key next to the data it
protects, no schema validation library at any boundary, and no linter.
Accepting them as "inherited" risks normalizing them. Accepted anyway
because rewriting them before understanding the codebase is exactly the
"big change first" pattern the methodology forbids, and because each fix
is a contained, separately-reviewable Tier-1/2 change.

**Revisit if any of these fire:**
- Jim approves Zod (or an alternative) — reopen to record the validation
  standard at each of the five boundaries named above.
- A keychain-backed credential store is proposed — reopen the "Secrets at
  rest" row; this is Tier 2 (touches credentials, needs migration path
  for existing `velo.key` users, and a rollback).
- Velo-Build's relationship to upstream is decided (fork vs. contributor
  vs. vendored) — that changes what "CI" means and whether npm/lockfile
  choices are ours to make.
- Any server-side component is proposed (sync relay, hosted AI proxy,
  telemetry) — the web default's rules (RLS, Hono, Better Auth) then
  apply to that component, and this ADR no longer covers the whole system.
- Node 18 reaches end-of-life in the toolchain actually used for
  releases — bump to 22 LTS per default.

## Consequences

- **Easier:** onboarding — `velo/CLAUDE.md`, `docs/architecture.md`, and
  `docs/development.md` are accurate and stay authoritative for *how the
  code works*; this ADR only governs *what we pin and how the standard
  applies*.
- **Harder:** the methodology's security baseline (`05-security.md`) and
  gate ledger (`04-gates.md`) assume a server. Each applicable item must
  be translated per the table above and recorded as satisfied or N/A in
  every handoff — "N/A" is a valid answer only with the reason given.
- **Follow-up work created (each its own brief, none started by this ADR):**
  1. PR-level CI: typecheck (`tsc --noEmit`), `vitest run`, `cargo clippy`,
     `cargo audit`, `npm audit`, secret scan, frozen-lockfile install. Clears
     the exception in `EXCEPTIONS.md`.
  2. Dependency proposal: Zod (boundary validation) — dependency block.
  3. Dependency proposal: Biome (lint/format) — dependency block.
  4. Threat pass on the LLM boundary: email content → AI features →
     `db/`/`fs`/`invoke()`/send. Tier 2.
  5. Evaluate OS-keychain credential storage (Tier 2; migration + rollback).
  6. Tighten `http:default` plugin scope to the CSP allowlist, or document
     why the wildcard is required.
- **Gates/docs that must change:** `docs/methodology/04-gates.md`'s
  "tenant-isolation harness" and "negative-authz suite" gates are N/A for
  this stack and should be marked so in the project's gate ledger when it
  is created, with IPC-boundary and LLM-output validation tests taking
  their place.
