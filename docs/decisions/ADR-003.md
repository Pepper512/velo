# ADR-003 — Where mail credentials live at runtime, once IMAP sessions are pooled

- **Status:** Accepted
- **Date:** 2026-09-02
- **Decider:** Jim (E2/P15 rev-2 re-confirmation; recorded as *(delegated)* in `LOG.md` via PR #33 and subject to his retroactive review)

## Question

Before E2/P15, every IMAP command carried an `ImapConfig` — host, port, username
and a **plaintext password or OAuth access token** — across the Tauri IPC
boundary. A delta sync sent that credential once per command, roughly
`2 + ceil(U/50)` times, and each command opened a connection, authenticated, and
logged out again.

Pooling keeps authenticated sessions alive in Rust. That changes what the
frontend must hand over and when, so three things need deciding and writing
down: **where the credential lives**, **what happens when it changes or is
revoked**, and **what a session id is worth to an attacker**.

## Decision

**1. The credential crosses the boundary only at session open.**

Exactly three commands may receive an `ImapConfig`:

| Command | Why |
|---|---|
| `imap_session_open` | The one that authenticates. |
| `imap_test_connection` | Account setup, before a session can exist. |
| `imap_raw_fetch_messages` | Decision 4(a): the raw-TCP fallback cannot run on a pooled session, so it carries its own. |

Plus `imap_raw_fetch_diagnostic`, which is **not compiled into release builds**.

Every other IMAP command takes an opaque `session_id`. This is enforced by test,
not by review: `poolBoundary.test.ts` spies on `invoke` across a round of mail
operations and asserts the password appears only in the commands named above.

**2. The pool holds no credential.**

A pool entry is a session, an account key and a timestamp. It is deliberately
**not** an `ImapConfig`. Rust therefore cannot re-authenticate a dead session; it
reports `NoSuchSession` and the frontend reopens, which is the only place a
credential exists to reopen with.

**3. A pooled session outlives the access token that opened it — deliberately, and with an escape.**

An OAuth access token typically lives an hour; a pooled IMAP session can outlive
it, because IMAP authenticates once at login and the server does not re-check the
token per command. That is not a bug, but it means **revocation does not reach a
live connection on its own.** So revocation is pushed explicitly:

- `clearConfigCache()` (password change) and OAuth refresh failure call
  `invalidateAccountCredentials()`, which bumps a **credential-version counter**
  for the account and evicts every session under the previous generation.
- Account deletion calls `closeAccountSessions()`.
- The reaper closes anything idle beyond `IDLE_TIMEOUT` (300 s).
- App exit drains the pool with a bounded best-effort LOGOUT.

**4. The account key is a connection configuration, not an account.**

`AccountKey` includes port, TLS mode, auth mechanism and the credential version —
not just `user@host`. Same user and host on port 143/STARTTLS is a different key
from 993/implicit TLS, and a rotated credential is a different key from the one
it superseded.

**5. A session id is a bearer credential, and 128 random bits are not the mitigation.**

The id is a plain `invoke` argument and lives in the module map of any window
performing mail operations. A sanitizer bypass executing same-realm in a
`thread-*` pop-out can hook `invoke` or patch the module and steal it, however
unguessable it is. The 128 bits from `getrandom` (Decision 2) are
**defense-in-depth against guessing, not against theft.**

What actually helps is P11's per-window capability grant, and binding a session
to the window label that opened it. **Neither is implemented yet** — this ADR
records that gap rather than implying it is closed.

## Options considered

| Option | Strongest case for | Strongest case against | Verdict |
|---|---|---|---|
| **Session id, credential only at open** | The credential crosses once per session instead of once per command; the pool cannot leak what it does not hold | Session id becomes a bearer token; revocation needs an explicit push | **Chosen** |
| Keep sending the config per command, pool by config hash | No new token to steal; revocation is automatic — the next command carries the new credential | Defeats the purpose: the credential is on the wire constantly, and the pool would have to hold or hash it to key on it | Rejected |
| Pool holds the config and re-authenticates dead sessions itself | Transparent recovery; no `NoSuchSession` round trip | Puts a plaintext password in a long-lived Rust structure with no window binding — strictly worse than the thing being fixed | Rejected |

## Consequences

**Better:** a delta sync authenticates twice instead of a dozen times; the
credential's exposure on the IPC boundary drops by an order of magnitude; the
UIDPLUS warning and other per-account facts now come from the pool's own record
rather than from a config the caller happened to pass.

**Worse, and accepted:** a stolen session id is usable from any window until the
binding lands; revocation is a push rather than a property; and a pooled session
is a piece of long-lived authenticated state that did not exist before, which the
checkout-removes-entry rule exists to keep honest.

**Unresolved, tracked not hidden:** per-window session binding and P11's
capability split. Both are named in the E2 brief's threat model, and neither is
done.
