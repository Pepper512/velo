2. Findings:

[M] F-01 — src/components/email/ThreadView.tsx — In `ThreadView.tsx`, line 208 inside `handleInstantIntro` retains `if (isNoReplyAddress(lastMessage.reply_to ?? lastMessage.from_address)) return;`. While requirement (d) was fixed inside `instantIntro.ts:replyTarget` (`replyTo || from || null`), this call site was overlooked. Because JavaScript's nullish coalescing operator `??` only falls back on `null` or `undefined`, a blank or whitespace-only `lastMessage.reply_to` (e.g., `""` or `"   "`) evaluates to the empty string rather than falling through to `lastMessage.from_address`. Consequently, `isNoReplyAddress("")` returns `false`, allowing the intro to proceed and reply to a no-reply address whenever `reply_to` is blank and `from_address` is a no-reply address. It should use `lastMessage.reply_to?.trim() || lastMessage.from_address` or a shared helper.

[M] F-02 — src/components/email/ThreadView.tsx — In `ThreadView.tsx` lines 72–84, resetting `aliases` via `setAliases(null)` inside `useEffect(() => { setAliases(null); ... }, [activeAccountId])` introduces a React state synchronization race when switching accounts. Because `useEffect` runs after the commit phase, when `activeAccountId` changes, React executes an initial render where `activeAccount` is updated to the new account, but `aliases` remains the previous account's array. During this render, `ownAddresses` computes `[activeAccount.email, ...aliases.map((a) => a.email)]`, producing a corrupted address list that combines the new account's email with the previous account's aliases before the effect can trigger a reset. This violates the stated guarantee that `null` prevents the intro from running on an invalid or uninitialized address list. To avoid a multi-render tear, the stale state should be cleared during render upon detecting an account ID change or `ThreadView` should be keyed by account.

[L] F-03 — src/services/composer/instantIntro.ts — `instantIntroUnavailableReason` does not check `isNoReplyAddress`, returning `null` (available) when the introducer is a no-reply sender. However, `ThreadView.tsx` passes `introUnavailableReason` directly to the action button while the click handler in `handleInstantIntro` explicitly guards against no-reply senders (`if (isNoReplyAddress(...)) return;`) with the comment `// The key path has no disabled button in front of it.` Because the reason function does not flag no-reply addresses, the button remains visually enabled; clicking it silently aborts without opening the composer or providing user feedback. Moving the no-reply check into `instantIntroUnavailableReason` would ensure the action button is properly disabled with an explanatory tooltip.

[N] F-04 — src/services/composer/instantIntro.ts — In `composerOptionsForIntro`, `resolveFromAddress(aliases, message.to_addresses, message.cc_addresses)` resolves the From address using only `aliases: SendAsAlias[]`. Note that this depends on code outside the delta: if `getAliasesForAccount` returns only secondary send-as aliases and excludes the primary account email (as strongly indicated by `ThreadView.tsx` explicitly constructing `[activeAccount.email, ...aliases.map((a) => a.email)]`), an intro delivered to `activeAccount.email` will not match any entry in `aliases`. `resolveFromAddress` will then fall back to the account's primary secondary alias (selecting an unintended sender alias) or return `null` (`fromEmail: null`). If `activeAccount.email` is omitted from the database aliases table, `resolveFromAddress` or `composerOptionsForIntro` needs access to `activeAccount.email`.
