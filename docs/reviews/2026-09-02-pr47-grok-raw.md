## Findings

1. **HIGH** — `src/services/imap/reconcilePass.ts` (`deleteConfirmed`)  
   **Concern:** Deletion is keyed only on `message_row_id`. There is no check that the row is still a live message in this folder (`imap_folder`, `imap_uid`, `moved_to IS NULL`), nor that it still matches the suspect’s generation.  
   **Trigger:** Between confirmation and delete, F-5 tombstones the row (`moved_to` set), COPYUID remaps it, or a UIDVALIDITY rollover reuses `imap-{account}-{folder}-{uid}` for a new message. User approval uses `confirmedInFolder` (any pass) and then this helper.  
   **Consequence:** Reconciliation deletes the cached copy of a move in progress, or the new message that recycled the id — not the vanished observation. Unattended `confirmedOnPass` is narrower, but it still calls the same helper.  
   **Fix:** Delete with a WHERE that includes `account_id`, `id`, `imap_folder`, `imap_uid`, and `moved_to IS NULL`. Skip (do not forget) rows that fail the match. Never delete tombstones here; F-5 owns those.

2. **HIGH** — `src/stores/uiStore.ts`, `ReconcileStopDialog.tsx`, `deleteConfirmedAfterUserApproval`  
   **Concern:** Stops are keyed `(accountId, folder)` only. `clearReconcileStop` ignores `uidvalidity`. A dialog can outlive a UIDVALIDITY change and then call `confirmedInFolder(account, folder, staleUv)`.  
   **Trigger:** Stop is on screen (or queued). Server rolls UIDVALIDITY. The existing-folder loop full-resyncs and `continue`s **before** the gate, so this pass never runs `applySearchAll` / generation purge (REQ-1.4). The stale stop remains. User clicks “Delete them”.  
   **Consequence:** Finding 1’s stale `message_row_id`s are deleted in the new generation.  
   **Fix:** Purge that folder’s suspects (and drop its stop) on UIDVALIDITY change, before `continue`. Key stops by `(account, folder, uidvalidity)` and refuse approval if current `folder_sync_state.uidvalidity` differs.

3. **HIGH** — `src/services/imap/reconcilePass.ts` (`finishReconcilePass`)  
   **Concern:** REQ-3.1’s hard stop is `confirmed * 2 > localRows` (and `localRows > 10`). The code does `planDeletions(localRows, eligible.length)` after `withoutPendingOps`.  
   **Trigger:** 20 live rows, 15 confirmed absent, 7 of those have pending ops → `eligible = 8`. `8 * 2 = 16` is not `> 20`, so no stop. Cap is 10; 8 rows delete unattended.  
   **Consequence:** A folder the spec says must delete nothing and ask the user still loses mail. Pending ops are a deferral, not a licence to bypass the stop.  
   **Fix:** `planDeletions(localRows, confirmed.length)`. If `plan.stop`, push the stop and delete nothing. Apply `withoutPendingOps` only to the batch you would have deleted when not stopped.

4. **HIGH** — `src/services/imap/imapSync.ts` + `reconcileFolderList`  
   **Concern:** REQ-3.3: a partial `UID SEARCH ALL` must delete nothing and clear nothing. The only completeness check is “IPC accepted a u32 list” (empty is valid). The list is never compared to `exists`.  
   **Trigger:** Gate opens (`exists !== live + new + flagged`). `imapSearchAllUids` returns a well-formed but short list — `[]` while `exists > 0`, or a truncated UID set. Applied twice. Folders with `≤ 10` live rows have **no** 50% stop and may be cleared in one confirmed pass (the 8-row test is that path).  
   **Consequence:** Two observations of a truncated list look like two-pass confirmation and delete real local mail.  
   **Fix:** In the same session as `UID SEARCH ALL`, re-read EXISTS (or fail closed if you cannot). If `serverUids.length === 0 && exists > 0`, treat as partial: do not call `applySearchAll`, do not add to `listed`, count a folder error. A same-session `|SEARCH ALL| vs EXISTS` mismatch should be the same. Do not use the earlier delta SELECT as a hard equality (race), but an empty list against a positive EXISTS is never a complete folder.

5. **HIGH** — `src/services/imap/imapSync.ts` (`attestPass` call)  
   **Concern:** REQ-1.2b: a failed or **partial LIST** invalidates the whole pass. Completeness here is `checkedFolders == syncableFolders`, and `syncableFolders` is whatever this LIST returned.  
   **Trigger:** LIST is short (truncated response, client filter, `raw_path` mismatch dropping a mailbox). Known local folders in `folder_sync_state` are simply not in the universe. Remaining folders can be `checked`, gates can list, `folderErrorCount === 0`.  
   **Consequence:** The pass attests and deletes in the folders it did see, which is exactly the “pass looks complete because we defined complete as the folders we saw” hole part 1 closed for `delta_check_folders`.  
   **Fix:** Fail attestation unless every previously synced folder path was either in this LIST and checked, or explicitly classified as gone (and then you still must not delete on that evidence alone). A LIST error/throw must go through `settleReconcile(false)` in `finally`, not skip finish.

6. **HIGH** — `ReconcileStopDialog.tsx` + `deleteConfirmedAfterUserApproval`  
   **Concern:** Mass delete is not one transaction; the UI treats any throw as “nothing was changed” and **always** dismisses the stop.  
   **Trigger:** (a) `CHUNK = 500`: first chunk commits, second throws. (b) `deleteConfirmed` commits message/thread deletes, then `forgetSuspects` (outside the txn) throws. (c) `onClose={dismiss}` while `loading={busy}` — Keep/overlay during an in-flight Delete. The failed-deletion test **asserts** the stop is cleared.  
   **Consequence:** Mail is already gone; the user is told nothing changed; the stop is gone so the next under-50% pass can continue unattended. Keep-during-busy races a delete the user just tried to cancel.  
   **Fix:** One transaction for the whole approval (or don’t clear the stop / don’t claim “nothing changed” unless `n === 0` and no chunk committed). Ignore `onClose` while `busy`. Dismiss only after success. On failure, leave the stop in place.

7. **MEDIUM** — `src/services/imap/imapSync.ts` (UIDVALIDITY `continue`)  
   **Concern:** REQ-1.4/1.5: a UIDVALIDITY change shall purge that folder’s suspects. This branch marks the folder `checked` and continues before the gate, so `reconcileFolderList` never runs.  
   **Trigger:** `deltaResult.uidvalidity_changed`.  
   **Consequence:** Old-generation suspects and a stale stop survive (Finding 2). The folder still counts toward attestation, so **other** folders may delete this pass. That is acceptable only if this folder’s suspects are gone.  
   **Fix:** `forgetSuspects` / purge other generations for that folder as soon as UV changes, then continue. Do not `markFetchCompleted` (no SEARCH ALL). Keeping it in `checkedFolders` after a successful full resync is fine.

8. **MEDIUM** — `withoutPendingOps`  
   **Concern:** Pending-ops are cached **per thread** from the first row seen, including that row’s `getPendingOpsForResource(accountId, message_row_id)`.  
   **Trigger:** Thread T, messages A then B; only B has a message-scoped pending op; A is first in `confirmedOnPass` order.  
   **Consequence:** B is treated as unblocked and can be deleted under REQ-3.4. If all ops are really thread-scoped (`resource_id` = thread id), this is latent; the extra message-id lookup makes it real.  
   **Fix:** Cache thread-level ops per thread; always query message-level ops per row (or stop pretending message ids are a resource).

9. **MEDIUM** — `ReconcileStopDialog` “Keep them”  
   **Concern:** Keep only `clearReconcileStop`. Those rows stay `confirmed_absent`. The next attested pass that falls back under 50% (new mail grew `localRows`, or Finding 3’s eligible filter) deletes them under the cap with no second question.  
   **Trigger:** User keeps 15/20. Five new messages arrive. 15 of 25 is not a stop. Cap deletes 10.  
   **Consequence:** “Keep” is not a hold; it is “ask again only if still catastrophic”. The copy says the folder is left as it is.  
   **Fix:** Either persist a per-folder hold until a SEARCH ALL shows the UID again, or make the copy and spec match (“we will start removing them in small batches if the folder is no longer more than half gone”).

10. **LOW** — `imapDeltaSync`  
    **Concern:** `settleReconcile` is copied onto three success/error returns, not a `finally`.  
    **Trigger:** Throw during threading/store after folders listed.  
    **Consequence:** No deletion (safe), but counters are not recomputed and the “every exit path” claim is false. A later edit that adds work to `finishReconcilePass` will inherit the hole.  
    **Fix:** `try { ... } finally { await settleReconcile(); }` with `attested` already computed (false if the pass did not finish cleanly).

11. **NIT** — `ReconcileStopDialog.test.tsx`  
    **Concern:** The failure case asserts `reconcileStops === []`, which locks in Finding 6.  
    **Fix:** After a failed delete, expect the stop to remain and no “nothing was changed” lie if any row was removed.

12. **NIT** — `folderSyncState.ts` / `setFlaggedNotExpunged` comment  
    **Concern:** “recompute, never zero” vs the harness, which correctly expects `0` when vanished local mail is not a ghost.  
    **Fix:** Comment should say “recompute from the observation, including zero; do not blindly RESET”.

## Questions

- On UIDVALIDITY change, does the existing full-resync **prune** local rows that are not on the server, or only upsert what it fetched? If it does not prune, this pass also never starts the suspect clock (gate is skipped).
- Does `upsertFolderSyncState` use `INSERT OR REPLACE` without `flagged_not_expunged`? In SQLite that is DELETE+INSERT and would reset the counter to 0 every last-uid write, forcing a SEARCH ALL every pass (NFR-1) and widening Finding 4’s window.
- Is `confirmedOnPass` ordered by `first_seen_at` so the cap is oldest-first (REQ-3.1)? That function is not in this diff.
- Should a UIDVALIDITY-changed folder be `fetchCompleted` for REQ-2.2? Current code: no list → `markFetchCompleted` is a no-op. That looks right; confirm the counter is not supposed to reset on resync.
- `getThreadMessageCount` includes tombstones, so a thread whose only leftover row is a tombstone is kept. That matches REQ-1.3 + F-5 — please confirm it is deliberate for user-approval deletes too.
- When `new_uids.length === 0` after a successful list, you mark fetch completed. Is “nothing to fetch” the agreed definition of REQ-2.2’s both-steps clause?
- `deleteConfirmedAfterUserApproval` deleting **any-pass** `confirmed_absent` is intended for the stop; should it refuse if the folder has not been SEARCH ALL’d since the stop was raised?

## What is good

- One pass id per account pass, `applySearchAll` only after a validated list, and end-of-pass deletes only `confirmedOnPass(..., this passId)` for folders in `pass.listed`. That is REQ-1.1 / 1.2(a) / 1.5 done properly; the harness Task 1 test is the right proof.
- Gate skip does not age (unlisted folders are not in `finishReconcilePass`’s delete loop). Unattested passes promote/re-stamp but do not delete; the next clean list re-stamps `last_verified_pass_id`.
- `shouldListFolder` includes incoming new UIDs and flagged ghosts, so a matching EXISTS does not pay a SEARCH ALL (NFR-1 / REQ-2.1). `exists === null` never lists.
- `gateOpened` is set before the list; a thrown list is a folder error, not a listed observation (`listed.set` is after `applySearchAll`). Malformed IPC → not listed, `attestPass(..., errorCount=1)`, `finish(..., false)`.
- `checkedFolders.add` before the per-folder `try` would be dangerous alone; `folderErrorCount > 0` fails the pass, so a listed-then-fetch-throw does not delete and does not recompute the counter (`fetchCompleted` stays false).
- Tombstones are excluded from the diff and from unattended delete; counter recompute is `|server − live|` after store, only when both steps completed, and vanished local mail is not a ghost.
- Cap is a slice limit, not a precondition; `≤ 10` full-clear is explicit; pending ops (thread id) actually defer; deletions log folder/UID/Message-ID; provider counter failures cannot fail the user action.
- SQLite-harness coverage for two-pass, unattested, cap, stop, UV purge **when a list runs**, pending ops, tombstones, and one pass id across folders is the right shape for a deleting change.
