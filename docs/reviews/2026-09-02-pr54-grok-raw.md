### Findings

**1. MEDIUM — `src-tauri/src/db/tx.rs` `TxManager::check` / `execute` / `select` / `reap_idle`**

Idle time includes in-flight SQL. `check` sets `last_used = Instant::now()` *before* the query await, and the tokio mutex is held for the whole statement, so the watchdog cannot run until the statement returns — at which point elapsed already includes the statement.

**Scenario:** One `INSERT` of a large body takes 31s, succeeds, callback issues the next `upsertAttachment` or `COMMIT`. Watchdog, queued on the mutex, runs immediately, `elapsed >= 30s`, `ROLLBACK`, id marked expired.

**Consequence:** A batch that was still active is aborted with `VELO_TX_EXPIRED`. Sync retries; the watchdog is firing on total statement time, not idle. REQ-1.3’s “idle, not total” is not what the code does.

**Fix:** Stamp `last_used` *after* `execute`/`select` complete (success or fail). Keep the mutex across the await if you want (it does serialize reap vs statement), but then a just-finished statement must look fresh. Add a test: begin, `sleep(idle)` *inside* a held execute (or mock a slow query), assert `reap_idle(30s)` returns `None` until after a quiet gap.

---

**2. MEDIUM — `src-tauri/src/db/tx.rs` `TxManager::begin` / `execute` / `finish` / `reap_idle`**

The same mutex is held across `pool.acquire()`, `BEGIN IMMEDIATE` (up to the 5s busy timeout), every statement, and `COMMIT`/`ROLLBACK`.

**Scenario:** Another window’s `db_tx_begin` or the watchdog runs while a statement or `BEGIN IMMEDIATE` is waiting on the pool or the SQLite write lock.

**Consequence:** Not a SQLite deadlock (the pin already holds the writer). It *is* a liveness hazard: `VELO_TX_BUSY` is delayed until IO finishes instead of returning immediately; a 5s `BEGIN IMMEDIATE` busy-wait freezes every other tx command; finding 1 is amplified because the watchdog’s first look after a long statement is instant.

**Fix:** Split the critical section. Under the lock: refuse if `current` is set / set a `starting` flag. Outside: `acquire` + `BEGIN IMMEDIATE`. Under the lock again: store or clear `starting`. Statement IO can stay under the lock (single connection, prevents concurrent use) if last_used is fixed.

**3. MEDIUM — `src/services/db/connection.ts` `beginWithRetry`**

`BUSY_RETRY_LIMIT * BUSY_RETRY_DELAY_MS` is 5s. A real sync batch (initial-sync chunk, F-5 re-key) can hold the Rust writer longer than that.

**Scenario:** Main window is inside `withTransaction` for a large IMAP chunk. Thread pop-out calls `withTransaction` (its own `txQueue`). Rust returns `VELO_TX_BUSY` for >5s.

**Consequence:** The pop-out fails with `VELO_TX_BUSY` instead of waiting. Same-window callers never see this (mutex). Cross-window is the case the retry was added for, and 5s is shorter than the 30s idle bound it comments on.

**Fix:** Retry until something on the order of the idle timeout (or backoff with a cap of 30s). Test: 51 busy replies, then success vs exhaustion.

**5. LOW — `src-tauri/src/db/tx.rs` `OpenTx` drop / `release`**

A connection with a raw `BEGIN IMMEDIATE` (not `Connection::begin()`, so sqlx is unaware) returns to the plugin pool if `OpenTx` is dropped without `release`.

**Scenario:** Panic in a command after `current` is set; process shutdown where `TxManager` drops while `tauri-plugin-sql` is still alive.

**Consequence:** The next plugin `execute`/`select` on that pooled connection runs inside a leftover transaction (or hits “cannot begin”). `release` already does the right thing on `COMMIT`/`ROLLBACK` failure (`detach` + `close`). Drop does not.

**Fix:** `impl Drop for OpenTx` that `detach()`s (cannot await `ROLLBACK` in `Drop`; closing is the safe fallback). Or open with `conn.begin()` so sqlx rolls back on drop.

**6. LOW — `src-tauri/src/db/tx.rs` `Inner.expired`**

Only the last reaped id is kept.

**Scenario:** Tx A idle-reaped; Tx B begins and is later reaped; owner of A then `commit`s.

**Consequence:** A gets `VELO_TX_UNKNOWN` instead of `VELO_TX_EXPIRED`. Harmless for control flow (both fail); TypeScript only silences rollback noise on `TX_EXPIRED`, so A’s late rollback would `console.warn`.

**Fix:** Small `HashSet` / ring of expired ids, or keep expired until the next successful `begin` *and* treat `TX_UNKNOWN` after a failed statement as quiet in `withTransaction` as well.
