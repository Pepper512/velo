**CHANGES REQUESTED**

Widening `img-src` to `https:` is the right fix for allowed mail, and the other directives are correctly left alone. The threat pass is wrong on blocked mail: this change removes the CSP backstop that was silently covering every image fetch the sanitizer does not rewrite. REQ-2 is not demonstrated.

---

### Findings

1. **HIGH** — `src-tauri/tauri.conf.json` (`app.security.csp` / `img-src`)  
   **Concern:** `img-src` is no longer a backstop. CSP `img-src` applies to more than `<img src>`: `srcset`, `<picture>`/`<source>`, CSS `url()` / `image-set()` (background, mask, border-image, list-style-image, cursor, `content`), HTML `background`, `<input type="image">`, `<video poster>`, SVG `<image href|xlink:href>`, `<link rel=icon>`. None of those become script (`script-src 'self'`, sandbox still has no `allow-scripts`, `connect-src` / `frame-src` unchanged). They do become **network image fetches**.  
   **Scenario:** Default “Block Remote Images” ON. Mail contains  
   `<td background="https://tracker.example/pixel.png">` or  
   `<div style="background-image:url(https://tracker.example/p.png)">` or  
   `<img src="cid:local" srcset="https://tracker.example/p.png 2x">`.  
   Spec describes `stripRemoteImages` as moving `src` → `data-blocked-src`. `style` / `srcset` stay on the allowlist.  
   **Consequence:** With the block ON, the webview now GETs arbitrary HTTPS URLs (IP, URL, Referer). Before this PR those loads died at CSP. The threat pass (“no `src` remains”) is false for every non-`src` vector.  
   **Fix:** Before this CSP lands, extend `stripRemoteImages` / `hasBlockedImages` to every `img-src` fetch vector (rewrite or drop `srcset`, `<source srcset>`, `poster`, `input[type=image][src]`, SVG `href`/`xlink:href`, `link[rel~=icon]`, HTML `background`, and `url()`/`image-set()` in `style` / `<style>`). Tests for each. Do not treat “sanitizer untouched” as residual-risk-free once CSP is `https:`.

2. **MEDIUM** — same CSP + `style-src 'self' 'unsafe-inline'`  
   **Concern:** Inline CSS is allowed; CSS `url()` is governed by `img-src`, not `script-src` / `connect-src`. That does not yield XSS (SVG-as-`<img>` does not run script; `@import` / remote stylesheets still fail `style-src`; `<iframe>` still fails `frame-src 'self'`; `http:` and `blob:` are still out of `img-src`). It does mean any `style` that survives sanitization is now a live tracker.  
   **Scenario:** Block ON, `<p style="background:url(https://evil/t.gif)">`.  
   **Consequence:** Same leak as (1), via the attribute email HTML always needs.  
   **Fix:** CSS URI stripping in the sanitizer (or a DOMPurify CSS hook that drops `url()` when blocking). Keep `http:` and `blob:` out of `img-src` (correct as written).

3. **MEDIUM** — `src/config/tauriConfig.test.ts` CSP parse (`Object.fromEntries`)  
   **Concern:** Duplicate directives: the map is last-wins; CSP is first-wins (later same-name directives ignored).  
   **Scenario:**  
   `img-src *; img-src 'self' data: https:`  
   Test reads the second, `toEqual(['self','data:','https:'])` passes; the webview uses `*`. Trailing `;` is fine (`filter(Boolean)`). Directive order is fine (keyed). Source order is pinned (good).  
   **Consequence:** The REQ-1.3 pin can go green on a policy the webview does not enforce.  
   **Fix:** Reject duplicate directive names; keep the first only (match CSP); then assert.

4. **LOW** — opted-in mail, cookie-bearing image GETs  
   **Concern:** `img-src https:` lets the iframe issue no-cors GETs to any HTTPS origin, including OAuth hosts already in `connect-src` (`login.microsoftonline.com`, `graph.microsoft.com`, `googleapis.com`, Yahoo). `img-src` cannot strip cookies.  
   **Scenario:** User allowlists sender (or turns the block off). Body has `<img src="https://graph.microsoft.com/v1.0/me">`.  
   **Consequence:** Tracking plus possible cookie-riding CSRF against whatever the webview cookie jar still holds. In scope of Jim’s decision; not in the threat pass.  
   **Fix:** Record it as residual until the Rust proxy; do not add `http:` or `blob:`.

5. **NIT** — same test, `not.toContain("http:")` / `not.toContain("*")`  
   **Concern:** Array `toContain` is exact-element. It does not catch `https://*` or `http://evil`. `toEqual` already pins the list; `'unsafe-inline'` is only implicit.  
   **Scenario:** `img-src 'self' data: https://*` — `toEqual` fails (good); the extra `not.toContain("*")` still passes.  
   **Consequence:** False confidence if someone later loosens `toEqual`.  
   **Fix:** Duplicate-key check (3); keep `toEqual` as the pin.

### Questions

- Does `stripRemoteImages` walk `srcset`, `<source>`, `poster`, `background`, CSS `url()`, SVG `href`, `input[type=image]`, `<link rel=icon>` — or only `img[src]`?
- Is the HTML `background` attribute on `body`/`table`/`td` in the DOMPurify allowlist?
- Does the webview share a cookie jar with the Microsoft/Google/Yahoo auth flows?

---

### What is good

- `https:` only; no `http:`, no `blob:`, no `*`. Matches REQ-1.1/1.2.
- `script-src`, `connect-src`, `frame-src`, `font-src`, `default-src`, `style-src` unchanged and pinned, including the key-set check for extra directives.
- Sandbox flags not relaxed; remote images still not a script/connect/frame primitive.
- Host list dropped in favor of the actual policy; CLAUDE.md records sanitizer-vs-CSP and “never add `http:`”.
- Trailing-semicolon and directive-order are handled; `img-src` source list is exact.
