## Verdict

**CHANGES REQUESTED** — the PR never deletes message rows itself, but unique reconcile pass-ids can confirm after one later delta, folder-gone can shrink the attestation set after two LIST omissions, and a UIDVALIDITY change can pin old UIDs to the new generation.

## Findings

1. **High — `src/services/imap/reconcileOp.ts` (`runReconcileOp` → `recordMissing(..., \`reconcile:${crypto.randomUUID()}\`, ...)`)**
   - **Concern:** REQ-4.5 is insert/refresh as *suspect*; the handler log even says “the next two passes confirm.” `recordMissing` promotes any suspect whose `first_pass_id` is from an *earlier* pass. A fresh UUID is always earlier than the next delta `passId` (and earlier than a second reconcile op).
   - **Trigger:** unknown-outcome move/delete → op sees UID absent → next `imapDeltaSync` lists the folder (EXISTS will usually already mismatch) and calls `recordMissing`.
   - **Consequence:** that UID becomes `confirmed` on the first later pass and `finishReconcilePass` may delete it in the same pass. Part 2’s two *list* observations collapse to one targeted SEARCH plus one list. Two reconcile ops (notice throw after a successful write, or overlapping folders) confirm with **no** delta pass at all. That is a real weakening of the two-pass rule.
   - **Fix:** do not reuse `recordMissing`’s promote path. Insert/refresh `status='suspect'` with a stable id (e.g. `reconcile:{folder}`) or a `refreshSuspects` helper that never promotes. Leave promotion to two delta passes. Drop the UUID.

2. **High — `src/services/imap/imapSync.ts` (folder-gone loop) + `src/services/imap/reconcilePass.ts` (`noteFolderMissing`)**
   - **Concern:** REQ-1.2b: a failed/partial LIST invalidates the pass; known folders stay in the attestation set. After two consecutive omissions, this path *removes* the folder from `syncStateMap` (so it leaves `knownFolders`), purges every suspect (`purgeOtherGenerations(..., 0)`), and clears the stop.
   - **Trigger:** (a) LIST succeeds but is short twice; (b) the folder still exists but `getSyncableFolders` drops it (`\Noselect` / `\Noinferiors`); (c) a large fraction of folders vanish from one LIST.
   - **Consequence:** messages are kept (good), but suspects and a >50% stop are voided, and the rest of the account can attest and delete. A later “new folder” initial sync upserts the same `imap-{acct}-{folder}-{uid}` ids; extras are not reconciled until a later gate. The notice “no longer exists on the server” is false for `\Noselect`. This is the one part-3 path that can undo part-2 protection without deleting rows here.
   - **Fix:** run folder-gone only after a LIST that is already classified complete (the same bit REQ-1.2b uses). If omitted folders exceed a sanity bound (e.g. >50% of `folder_sync_state`), treat the LIST as partial: bump nothing, remove nothing, fail attestation. Distinguish “not selectable” from “not present”; do not `clearReconcileStop` / purge suspects unless the folder is actually gone. Snapshot completeness before mutating `syncStateMap`.

3. **High — `src/services/imap/reconcileOp.ts` (`runReconcileOp` reads `getFolderSyncState` at handler time; params have no `uidvalidity`)**
   - **Concern:** UIDs on the op are from the generation at enqueue. Suspects are recorded against *current* `uidvalidity`.
   - **Trigger:** UIDVALIDITY changes (or an initial sync writes a new generation) while a reconcile op is pending; old live rows may still use the old UIDs (identity is `imap-{account}-{folder}-{uid}`).
   - **Consequence:** SEARCH of those UIDs in the new mailbox is usually empty → `recordMissing(newGen, oldUids)`. A reused UID can confirm and then part 2 deletes the *new* message row. Cross-generation suspects also survive `invalidateFolderSuspects` because they were written *after* the change, under the new generation.
   - **Fix:** put `uidvalidity` in `ReconcileParams` at enqueue. If `state.uidvalidity !== params.uidvalidity` (or state is missing), drop the op; do not record. `degradeReconcileOp` can still `setForceList` so the new generation gets a full list.

4. **Medium — `src/services/imap/imapSync.ts` (belt: `(deltaResult.exists ?? 0)` and `gateOpen = false`)**
   - **Concern:** REQ-2.1/2.3 may skip a full list only when the NOT DELETED count agrees with live + incoming. Closing the gate when `exists` is null treats “unknown size” as “nothing vanished.”
   - **Trigger:** `shouldListFolder(null, …)` opens the gate (typical fail-open); belt is due; `notDeleted === liveCount + new_uids.length`.
   - **Consequence:** `reconcileFolderList` never runs, so the empty-vs-positive-EXISTS throw never fires. A vanished UID plus a matching arrival, or a null EXISTS, can skip the list. Ghosts are also written as `max(0, 0 - notDeleted) = 0`, wiping a real `flagged_not_expunged`.
   - **Fix:** if `deltaResult.exists == null`, do not belt-skip and do not call `setFlaggedNotExpunged`. Forced lists should likewise refuse `applySearchAll` when `exists` is null (part 2’s unchecked path). Recompute ghosts only from a SELECT on the *same* session as `UID SEARCH NOT DELETED` (stale `deltaResult.exists` is a drift source, usually conservative, but not when it coalesces with null).

5. **Medium — `src/services/emailActions.ts` (`executeQueuedAction` → `executeViaProvider` only)**
   - **Concern:** REQ-4.1 is on any `VELO_OUTCOME_UNKNOWN:` from a move/delete, interleaved with the notice path. The online `executeEmailAction` catch enqueues reconcile ops; the queue flush path does not.
   - **Trigger:** offline archive/trash/move/delete (optimistic apply + enqueue user op) → later `UID MOVE`/`UID STORE` times out unknown → `classifyError` is indeterminate / not retryable → op marked `failed`.
   - **Consequence:** no targeted SEARCH, no suspects, no REQ-4.3 degrade. Local rows stay in the optimistic post-move state with no observer. Permanent-delete is worse: cascade may already have dropped rows, so even a later op would no-op on `absent ∩ live`.
   - **Fix:** in `executeQueuedAction` (or the processor’s indeterminate branch), if `isMoveOrDelete` and `VELO_OUTCOME_UNKNOWN`, `enqueueReconcileOps` from `params.messageIds` before marking failed. Do not retry the move.

6. **Medium — `src/services/queue/queueProcessor.ts` (`updateOperationStatus(failed)` then `degradeReconcileOp` in try/catch)**
   - **Concern:** REQ-4.3: three strikes must not vanish — force-list + notice. `JSON.parse(op.params)` or `setForceList` can throw; the warn swallows it. Order is fail-then-degrade.
   - **Trigger:** malformed params, missing `folder_sync_state` row, or `setForceList` failure after the third strike (or any non-retryable error, which degrades on *first* failure).
   - **Consequence:** row is `failed`, no `force_list`, no notice. The inconsistency has no observer. `incrementRetry` is skipped, so there is no second chance.
   - **Fix:** degrade *first* (folder from `resource_id` if params do not parse: `reconcile:{folder}`). If degrade fails, leave the op `pending` so it retries. Only then mark `failed`. Do not catch-and-forget.

7. **Medium — `src/services/imap/reconcileOp.ts` (`withSession(accountId, "interactive", …)`)**
   - **Concern:** REQ-4.1 asks for a fresh session; REQ-4.5 says repairs must not head-of-line block user writes. Queue work uses the interactive pool.
   - **Trigger:** a reconcile op runs while the user is moving/reading mail.
   - **Consequence:** the targeted SEARCH can take the interactive connection (or wait behind the user, or the reverse). Sync is serialized process-wide; interactive is not, so this also races a delta pass on the same folder (feeds finding 1).
   - **Fix:** `withSession(..., "sync", …)` (or a background kind). Keep queue `ORDER BY (operation_type = 'reconcile') ASC`.

8. **Low — `src/services/imap/imapSync.ts` (`beltDue` only when `gateOpen && pass % 10 === 0`)**
   - **Concern:** REQ-2.3: persistent mismatch after a list should *fall back* to a NOT DELETED count once per N=10 rather than listing every pass. Here, non-multiples still full-list whenever the gate is open; the belt only cheap-skips on the 10th. `flagged > 0` is also a proxy for “no UIDPLUS”; other clients’ `\Deleted` with Velo’s counter at 0 never belts, so those accounts still list every pass.
   - **Trigger:** no-UIDPLUS ghosts keep the gate open; or only other-client `\Deleted`.
   - **Consequence:** not a vanish hole (you list *more* often than the spec). Cost-saving intent is only ~1/10 of listings, and only after Velo itself has incremented `flagged_not_expunged`. A real vanish is **not** delayed 10 passes in this code — that delay would appear only if you inverted the belt to *skip* lists on non-multiples.
   - **Fix:** if you want spec-faithful cheapness, on `flagged > 0` (or a stored no-UIDPLUS bit) skip the full list unless `beltDue` or `forced`, and let a disagreeing count open the list. Do not delay vanishes on UIDPLUS / `flagged === 0` accounts. Document that ticking `reconcile_passes` on closed-gate passes is the clock (that part is fine).

9. **Low — `src/services/db/pendingOperations.ts` (`compactQueue` merge)**
   - **Concern:** REQ-4.2 newest-plus-union, max attempts, pending only — that is right, and not resetting `retry_count` avoids the infinite-retry hole. `merged` is `{...newest.params, uids}` so a newest row without `kind` stays unlabelled (REQ-4.4). `JSON.parse` is unguarded. `resourceOps` last element is assumed newest.
   - **Trigger:** a hand-inserted/malformed newest row; non-sorted group.
   - **Consequence:** queue surface may hide `kind: "repair"`; a parse throw aborts compaction for the whole account.
   - **Fix:** always set `kind: "repair"` on merge; try/catch per row; sort by `created_at` before picking newest.

10. **Nit — `src/services/imap/client.rs` (`count_not_deleted`)**
    - **Concern:** `UID SEARCH NOT DELETED` still returns every matching UID; you only use `len()`. Same wire shape as a full list; savings are TS-side (`applySearchAll` skipped) and a smaller set than `ALL` when ghosts exist.
    - **Trigger:** large no-UIDPLUS mailbox on pass 10, 20, …
    - **Consequence:** the “cheap belt” may not be cheap. Not a correctness bug.
    - **Fix:** none required for F-4; if it shows up in traces, consider a server that speaks `STATUS` / `SEARCH RETURN (COUNT)` later (new capability, not this PR).

11. **Nit — `src/services/imap/reconcilePass.ts` (`purgeOtherGenerations(accountId, folder, 0)`)**
    - **Concern:** “other than 0” is used as purge-all. Harmless while every suspect has `uidvalidity > 0` (`runReconcileOp` already skips `uidvalidity === 0`).
    - **Fix:** a real `purgeAllSuspects(account, folder)` so the sentinel is not load-bearing.

## Questions

- Is a short LIST already a failed/partial LIST in this codebase (REQ-1.2b), so folder-gone only runs when LIST is known complete? If yes, finding 2 shrinks to the `\Noselect` / not-syncable case — still a notice and stop-clear bug.
- What does `shouldListFolder(null, …)` return, and does `reconcileFolderList` refuse `applySearchAll` when `exists` is null? The forced-list test uses a closed gate with a numeric EXISTS; the null case is untested.
- When the belt sets `gateOpen = false`, is the folder still added to `checkedFolders` (same as a naturally closed gate)? If not, every 10th pass fails attestation globally.
- Does `deleteFolderSyncState` have any FK cascade onto `messages` / `threads`? From this diff it should not; that is the whole invariant.
- `bumpReconcilePasses` before the gate, including closed-gate passes: intended clock? (I think yes.) Confirm you do not also bump on the UIDVALIDITY-changed branch, or force will be the only way to list that generation if you need it.
- `permanentDelete`: enqueue is *before* revert, which is correct for IDs; at run time you only record live rows. If revert failed, the op no-ops. Is the existing unknown-outcome notice still shown so the user is not silent?
- Compaction `retry_count = max` vs `incrementRetry` marking failed at `retry_count+1 >= max_retries`: exhausted uses the row’s `max_retries` (3). Any old reconcile row with default 10 would get ten strikes before degrade — worth a one-line assert that enqueue always writes 3.

## What is good

- **REQ-4.2 / 4.4 / 4.5 queue shape is mostly right:** `resource_id = reconcile:{folder}`, `kind: "repair"`, `max_retries` 3, user ops ordered first, compaction unions UIDs and *keeps* max attempts, pending-only.

- **Belt is skipped for `force_list`**, and `setForceList(false)` runs only after `reconcileFolderList` returns, so a throw leaves the folder forced. Empty-set SEARCH is short-circuited before pool checkout; UID sets are validated on both sides of the FFI; TS rejects extras and non-integers.
- **`groupImapIdsByFolder` uses the last hyphen**, so `Projects-2026-Q3` survives; UID 0 is dropped.
- **Online unknown move/delete does not retry the write** (no duplicate mail) and still reverts the optimistic update.
