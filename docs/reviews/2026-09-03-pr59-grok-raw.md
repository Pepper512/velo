### Findings

1. **MEDIUM** — `src/services/db/accounts.ts` `insertImapAccount` vs `AddImapAccount` test/save vs `buildSmtpConfig`

   **Concern:** The form test uses `resolveSmtpCredentials(...).password` as-is. Save passes that same string in, then insert does `account.smtpPassword ? encryptValue(...) : null`. Empty string is falsy, so it is stored as `NULL`. `buildSmtpConfig` then does `smtp_password ?? imap_password`.

   **Scenario:** User unticks “Use same credentials as IMAP”, sets SMTP username `relay-user`, leaves SMTP password blank, saves (no `required` on the field; save is not shown gated on a green SMTP test).

   **Consequence:** SMTP test authenticates as `relay-user` / `""`. The row is `smtp_username='relay-user'`, `smtp_password=NULL`. Send authenticates as `relay-user` / IMAP password. Same class of bug as #252: test and later send disagree. Also violates REQ-1.2 (unticked → persist the password entered; empty→NULL is specified only for username).

   **Fix:** When the checkbox is off, require a non-empty SMTP password before save. In insert, treat only `null`/`undefined` as “same as IMAP”; never coerce `""` to NULL. Prefer `smtpPassword == null ? null : encryptValue(smtpPassword)` so the omit path and the empty-string path stay distinct.

2. **MEDIUM** — `src/services/imap/imapConfigBuilder.ts` `buildSmtpConfig` × `decryptAccountTokens`

   **Concern:** Fallback is indistinguishable from “this field was present and decrypt failed.” `ENCRYPTED_FIELDS` will run `smtp_password` through the fail-closed reader, but if that reader nulls a failed field and still returns the account, the new `?? imap_password` path sends with the IMAP secret.

   **Scenario:** Split-credential account; `smtp_password` ciphertext is corrupt or the key cannot decrypt it. Banner may say “SMTP password”; send still builds `password: imap_password`.

   **Consequence:** Decrypt failure fails *open* for SMTP (wrong credential used, or a send that should have been blocked succeeds). Pre-28 accounts are fine (column was always NULL). Only split-credential rows.

   **Fix:** Keep account-level fail-closed (do not return a sendable account if any `ENCRYPTED_FIELDS` entry fails). Do not use IMAP fallback unless the column was NULL in the row, not “nulled after a decrypt error.” Add a test: `smtp_password: "not-valid-ciphertext"` → no usable SMTP config, banner label `"SMTP password"`, and `buildSmtpConfig` is never reached with a null that means “use IMAP.”

3. **MEDIUM** — `src/components/accounts/AddImapAccount.tsx` (no test file in this diff)

   **Concern:** #252 lived entirely in the form. Resolver unit tests cannot catch a second identical-ternary. Save still special-cases the checkbox (`form.samePassword ? {} : resolveSmtpCredentials(...)`) instead of always resolving and then persisting NULL/NULL when ticked.

   **Scenario:** Regression: save spread omits `smtpPassword` again, or passes `form.password` for both arms; tests still pass.

   **Consequence:** Setup green, first send fails — the original bug, undetected.

   **Fix:** Component (or handler) test, two cases:
   - checkbox **off**, `smtpUsername: "relay-user"`, SMTP password `["smtp","pass"].join("-")` → `insertImapAccount` called with those two fields, and `smtp_test_connection` invoked with the same password.
   - checkbox **on**, SMTP fields filled in state → insert **not** given `smtpPassword` / `smtpUsername` (both NULL/omitted).

4. **LOW** — `imapConfigBuilder.ts` `buildSmtpConfig` (`??` vs `||`)

   **Concern:** Username uses `||` (empty string → fallback). Password uses `??` (empty string sticks). Insert already turns `""` into NULL, so this is latent, not hit by the form today.

   **Scenario:** Any writer stores `smtp_password = ""` (or decrypt yields `""`).

   **Consequence:** SMTP AUTH with an empty password instead of the IMAP password; existing NULL rows unchanged.

   **Fix:** One “is set” helper for both fields: non-null and non-empty (after trim for username). Test: `smtp_password: ""`, `imap_password: "secret123"` → password is the IMAP one **or** reject the row; pick one and lock it.

5. **LOW** — `imapConfigBuilder.test.ts` `buildSmtpConfig`

   **Concern:** Per-field fallback is only tested one way (SMTP password set, username NULL). REQ-1.4 is symmetric.

   **Scenario:** `smtp_username: "relay-login"`, `smtp_password: null`, `imap_password: "secret123"`.

   **Consequence:** A username-only override could later be wired wrong (e.g. requiring both fields) without a red test. This is the “relay user, same app password” case.

   **Fix:** Assert that config is `{ username: "relay-login", password: "secret123" }`. Also assert the full config object for all-NULL SMTP columns (REQ-2.1 asked for exact object equality, not just user/pass).

6. **LOW** — `migrations.test.ts` migration 28

   **Concern:** Test only checks `PRAGMA table_info` contains the two names. Does not show a pre-28 row surviving with NULL SMTP columns, and does not show 28 is skipped on re-run (that is only the generic “second run applies nothing”).

   **Scenario:** Harness applies 1…27, inserts an account, applies 28.

   **Consequence:** A NOT NULL / DEFAULT mistake would not be caught; existing send behavior is the whole compatibility bet.

   **Fix:** After 28, `SELECT smtp_username, smtp_password` on that row is `(null, null)`. Relying on the version table for idempotency is fine if that remains the house pattern.

7. **NIT** — `AddImapAccount.tsx` above `mapSecurity`

   **Concern:** The `mapSecurity` JSDoc now sits on `smtpCredentialInputs`.

   **Fix:** Move the comment back onto `mapSecurity`.

8. **NIT** — `AddImapAccount.tsx` form state

   **Concern:** Checkbox label is “credentials”; the flag is still `samePassword`. Easy to treat it as password-only again.

   **Fix:** Rename to `sameCredentials` (or map it only at the resolver boundary, which you already do).

### What is good

- `smtp_password` is on `ENCRYPTED_FIELDS` with a banner label; insert encrypts before bind; tests keep secrets out of literal form.
- Migration 28 is additive `TEXT` NULL columns; contract `DROP COLUMN` is recorded, not executed; pre-28 rows stay NULL and the NULL fallback matches today’s user/pass.
- OAuth still authenticates SMTP with the access token; `insertOAuthImapAccount` left alone; stored SMTP password is ignored when `auth_method === "oauth2"` and a token is passed.
- Resolver is the right seam: OAuth → token and no username override; ticked → IMAP password, username `null`; unticked → SMTP fields, blank username → `null`.
- Per-field fallback in `buildSmtpConfig` is the right rule; mocks grew the new fields so `DbAccount` stays complete.
