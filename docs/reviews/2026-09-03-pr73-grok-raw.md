```ts

```

`StaleCredential` only refuses a session tagged with a *retired* generation. It does not refuse a session authenticated with a revoked/old credential and tagged with the *current* generation.

Interleaving:

1. Window A has already built `config` (old password / still-valid access token) and invoked `imap_session_open`.
2. Window B runs `imap_sessions_invalidate`; `bump_credential_version` moves the account to `V+1`, evicts what is in the map, then emits `velo-imap-sessions-invalidated`.
3. Window A’s command now runs: `credential_version()` returns `V+1`, `connect(&config)` still uses the pre-bump secret, `insert` sees `version == current` and **accepts**.
4. `onSessionsInvalidated` has already fired. Window A often has nothing to forget yet (`accountIdents` is written only *after* a successful open). It then caches the new id.

This is the dual of the race SPEC-E2-3 REQ-2.1 names. Password change often dies at LOGIN; OAuth refresh-failure does not — the whole point of invalidation is that a pooled connection outlives the token, so that token still logs in. The result is a current-generation session that survives until the next bump or the idle reaper.

Same-window `pendingInvalidations` does not cover it: the wait is only on *this* window’s pending promise, and only if it is already in the map when `openSession` reads it.

Fix:

- Frontend: keep a monotonic `invalidationEpoch`, increment it in both `invalidateAccountCredentials` and `onSessionsInvalidated`. Snapshot it before `imapSessionOpen`. If it changed when the id comes back, `imapSessionClose(id)` (do not cache) and take the existing one-shot reopen path.
- Frontend: `await listen(...)` *before* the first open, not fire-and-forget after flipping a boolean — otherwise the first open can miss the event that would bump the epoch.
- Do not treat “insert’s generation matches current” as “this socket was authenticated with the current secret.” Document that residual in the threat pass if you refuse to fence in-flight opens.

**2. MEDIUM — `src/services/imap/sessionManager.ts` `invalidateAccountCredentials`**

```ts
const ident = accountIdents.get(accountId);
forgetAccount(accountId);
if (!ident) return;
```

If the window that handles password change / OAuth refresh failure has never called `withSession` for that account, this returns without bumping the pool and without emitting the new event. Other windows keep using live sockets authenticated with the rotated credential. The event added in this PR cannot fire from a bump that never happens.

This is older than the PR, but this PR’s threat model is “a rotated credential is never served from the pool,” and the new protocol does not close the path.

Call `imapSessionsInvalidate` unconditionally on a credential change. Keep `accountIdents` as a fast path, not the only path.

**3. LOW — `src/services/imap/sessionManager.ts` `ensureInvalidationListener`**

```ts
if (invalidationListenerStarted) return;
invalidationListenerStarted = true;
listen<SessionsInvalidatedPayload>(SESSIONS_INVALIDATED_EVENT, (event) => {
  onSessionsInvalidated(event.payload);
}).catch((err: unknown) => {
  console.warn("[sessionManager] Could not listen for session invalidations:", err);
});
```

The flag is set before `listen` resolves. A reject is sticky: every later `withSession` sees the flag and never retries. Events in the gap before the Promise resolves are missed. Pop-outs then pay the `NoSuchSession` round-trip this event exists to avoid — and finding 1 gets worse, because the epoch fence never sees those events.

Fix: set the flag only after `listen` resolves; on reject, clear it (or retry with backoff). Have `withSession`/`openSession` await the registration, not just kick it.

**4. LOW — `src-tauri/src/commands.rs` `imap_sessions_invalidate`**

```rust
for session in pool.bump_credential_version(&ident) {
    logout(session).await;
}
let _ = app.emit(
    SESSIONS_INVALIDATED_EVENT,
    SessionsInvalidated { username: ident.username, host: ident.host },
);
```

Two problems.

- The map is already emptied by `bump` before this loop. The event is then delayed by up to `PER_ACCOUNT_CAP * LOGOUT_TIMEOUT` (6s today, linear in the cap later). Other windows keep invoking with cached ids and fail `NoSuchSession` for the entire LOGOUT budget — the behaviour REQ-3.1 was written to remove.
- `let _ = app.emit(...)` swallows a failed broadcast. No window forgets.

Fix: emit immediately after `bump_credential_version` returns, *then* LOGOUT (preferably `join_all`, matching the exit hook). Log emit failure. The new connect does not need the old sockets to have finished LOGOUT; they are already out of the map.

**5. LOW — `src-tauri/src/commands.rs` `spawn_logout`**

```rust
fn spawn_logout(session: ImapSession) {
    tauri::async_runtime::spawn(logout(session));
}
```

Used for the cap victim (`insert -> Ok(Some(victim))`) and for `release_ok` orphans. The `JoinHandle` is discarded. On runtime shutdown those tasks are dropped, and a *clean* session is dropped without LOGOUT — the thing this PR says the pool no longer does. `drain` on `ExitRequested` will not see them; they are already out of the map.

Fix: track in-flight LOGOUT tasks and join them under the existing exit timeout, or have the exit hook wait on a side set of “owned but not in the map” sessions. At minimum, document that fire-and-forget LOGOUT is best-effort and not covered by the exit drain.

**6. LOW — `src-tauri/src/imap/pool.rs` `insert`**

```rust
debug_assert!(is_well_formed_id(&id), "the pool only issues well-formed ids");
// ...
inner.entries.insert(id, Entry { session: Some(session), ... });
Ok(evicted)
```

Release builds never shape-check `id`. A duplicate key overwrites the previous `Entry` and **drops that clean session inside the map lock**, with no `Option<S>` returned to the caller. `acquire`/`remove` will then refuse a malformed id before lookup, so a bad insert is also unreapable except via `drain`/`bump` by identity.

128-bit random ids make collision a curiosity; the API contract this PR writes (“the pool never drops a clean session on its own”) is still false on this path.

Fix: if `entries.contains_key(&id)`, return `Err((PoolError::..., session))` (or return the displaced session as the victim). Validate shape in release, not only `debug_assert!`.

**7. LOW — `src/services/imap/sessionManager.ts` `onSessionsInvalidated`**

```ts
export function onSessionsInvalidated(payload: SessionsInvalidatedPayload): void {
  for (const [accountId, ident] of accountIdents) {
    if (ident.username === payload.username && ident.host === payload.host) {
      forgetAccount(accountId);
    }
  }
}
```

No runtime check that `payload` has string `username`/`host`. A bad emit throws inside the Tauri listener. Depending on the event plugin, that can kill subsequent deliveries for this window.

The payload is also account identity broadcast to every webview. That is not a session id or a secret, but it is PII, and any renderer that can emit the same event name can force every window to drop caches (login DoS, not session theft).

Fix: drop events that fail a narrow schema check (`typeof username === "string" && typeof host === "string"`). Keep the “identity only” rule. Threat-pass: renderer-emitted events are a DoS of cached ids, not an authz bypass (ADR-003 still keys on possession of the id).

**8. LOW — threat pass gap: in-flight ops are not revoked**

`bump_credential_version` skips checked-out entries (`session: None`). `with_pooled_session` then runs the command to completion against the socket that invalidation was meant to kill. On `Ok`, `release_ok` returns the orphan and `spawn_logout` runs *after* the side effect (MOVE/APPEND/DELETE/SETFLAGS included).

That follows from checkout-takes-the-session; it is not a regression. It is also not in the threat pass as an accepted residual.
