### 2. Findings

[H] F-01 — src/components/layout/EmailList.tsx — Lines 572–577: The scroll-to-selection effect depends exclusively on `[selectedThreadId]`. When the component mounts or routes directly to a thread (e.g., initial application boot or deep-linking to `/inbox/t150`), `selectedThreadId` is populated on first render while `items` is still empty (`itemsRef.current.length === 0`). `itemsRef.current.findIndex(...)` evaluates to `-1` and `scrollToIndex` is skipped. When the asynchronous query completes and `items` populates, `selectedThreadId` does not change, so the effect never re-fires. As a result, opening the client or navigating to a route with an existing selection fails to scroll the selected thread into view, violating REQ-3.3.

[H] F-02 — src/components/layout/EmailList.tsx — Lines 580–584: The `loadMore` effect triggers whenever `lastRenderedIndex >= 0 && lastRenderedIndex >= items.length - 5` without checking `hasMore` or `!loadingMore` (both available in scope from lines 551–552). For any folder or search result set with five or fewer threads, `items.length - 5 <= 0`, causing `loadMore()` to execute immediately on mount even if all rows are already loaded. Furthermore, when `loadMore()` sets `loadingMore = true`, `buildListItems` appends a `"loading"` footer (line 551; `listItems.ts:107`), incrementing `items.length` by 1. Because `items.length` is in the effect's dependency array, the effect re-runs immediately while the previous request is still in flight, firing duplicate fetches. When `hasMore` is false, it continues to trigger `loadMore()` on every render where the tail of the list is visible.

[M] F-03 — src/components/layout/EmailList.tsx — Line 574: `findIndex` explicitly constrains its search to `it.kind === "thread" && it.threadId === selectedThreadId`. Expanded bundle rows produce items of kind `"bundle-child"` (defined in `src/services/inbox/listItems.ts:84` and rendered at lines 659–674 with `isSelected={thread.id === selectedThreadId}`). Because bundle children are excluded by `it.kind === "thread"`, selecting a thread inside an expanded bundle (via `j`/`k` keyboard shortcuts or click selection) yields `-1`, preventing the virtualizer from ever scrolling a selected bundle child into view and violating REQ-3.3 and REQ-3.4.

[M] F-04 — src/components/layout/EmailList.tsx — Lines 586–595: The first-paint stagger logic couples two effects across renders: an effect resetting `firstPaintRef.current = true` on `[activeAccountId, activeLabel, activeCategory]`, and an unconstrained effect resetting `if (items.length > 0) firstPaintRef.current = false;` on every commit. During the render where `activeCategory` or `activeLabel` changes, `staggerOnThisPaint` reads `firstPaintRef.current`, which is still `false` from previous renders. Then, during the post-render effect phase, Effect 1 sets `firstPaintRef.current = true`, but Effect 2 runs immediately after in the same tick and flips it back to `false` if `items.length > 0` (which is true for synchronous in-memory category changes or cached folder threads). Consequently, no render ever observes `firstPaintRef.current === true` on category/folder changes, breaking REQ-3.4's stagger behavior on navigation.

[M] F-05 — src/components/layout/EmailList.virtual.test.tsx — Lines 74–78, 129–155: The test suite stubs `globalThis.ResizeObserver` with an empty mock (`observe() {}`), which prevents `@tanstack/virtual-core`'s `measureElement` from receiving observation callbacks; dynamic row measurement is completely unexercised, allowing tests to pass strictly on `estimateSize`. Furthermore, test 2 ("brings a far-away selected thread into the rendered window", lines 140–148) masks F-01 by mounting with `nav.selectedThreadId = null` and mutating it only after the thread store has resolved. Finally, the test suite omits two test requirements explicitly mandated by the brief under SB-3 Tasks: bundle row positioning and `loadMore` firing near the end.

[L] F-06 — src/components/layout/EmailList.tsx — Lines 661–663, 678–680, 814–834: `buildListItems` strips the `Thread` objects down to `threadId`, forcing `renderItem` to look up `threadMap.get(item.threadId!)`. If a thread is missing or temporarily desynced in `threadMap`, `renderItem` returns `null`. However, the outer virtual row wrapper at lines 817–828 still mounts with `ref={virtualizer.measureElement}`. Because it contains no children, it collapses to a height of `0px`, causing `measureElement` to cache a zero height for that item key in TanStack Virtual's internal cache, corrupting the scroll layout.

### 3. What Was Verified and Found Correct

- **Dependency Pin (REQ-3.5):** `package.json` pins `"@tanstack/react-virtual": "3.14.10"` exactly without semver range prefixes (`^` or `~`).
- **Divider Rule Fix (REQ-3.2):** `buildListItems` in `src/services/inbox/listItems.ts` checks `previousPinned && !thread.isPinned` strictly over `input.threads` (`visibleThreads`), eliminating the latent bug where the old code indexed `filteredThreads` while iterating `visibleThreads`.
- **Row Height Estimation (REQ-3.2):** `estimateRowHeight` accurately models densities (`44` for compact, `72` for default, `88` for spacious, `+28` for divider, `64` for bundle headers, `40` for footers), ensuring initial scrollbar stability.
- **Key Stability across Item Kinds:** Item keys (`bundle-${category}`, `bundle-${category}-${thread.id}`, `thread.id`, `footer-loading`, `footer-all-loaded`) are unique across all row types and remain stable across data reloads.
- **Virtualizer Container Layout:** The relative scroll container sized to `virtualizer.getTotalSize()` with absolutely positioned child wrappers using `translateY(${virtualRow.start}px)` and `overscan: 8` strictly matches REQ-3.1.
- **Store-Backed State Unbroken (REQ-4):** Thread selection, multi-select ranges, `j`/`k` indexing, and `@dnd-kit` draggable handles on `ThreadCard` `<button>` nodes operate independently of the DOM and are not regressed by virtualization.
