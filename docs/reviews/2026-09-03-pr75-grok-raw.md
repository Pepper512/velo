HIGH — `src-tauri/capabilities/content.json` (fs block, lines 16–27) and `src/config/capabilities.test.ts` (`REQUIRED_IN_CONTENT` comment on `fs:allow-write-file`)

Exact grant:

```
"fs:allow-appdata-read-recursive",
"fs:allow-appdata-write-recursive",
"fs:allow-read-file",
"fs:allow-write-file",
"fs:allow-exists",
"fs:allow-mkdir",
{ "identifier": "fs:scope", "allow": [{ "path": "$APPDATA" }, { "path": "$APPDATA/**" }] }
```

The comment on the required list is “attachment cache, velo.key” / “velo.key on first run.”

A sanitizer bypass in `thread-*` / `compose-*` can now read and overwrite everything under app data: `velo.key`, the DB file, config, the attachment cache. That is not a residual you get for free from “drafts and attachments.” First-run key creation is a main-window path; a pop-out does not need it. Recursive write of `$APPDATA/**` is also a second write channel onto the SQLite file that sits beside `sql:allow-execute`.

Fix: scope content to the attachment-cache directory only (e.g. `$APPDATA/attachments` + `$APPDATA/attachments/**`). Drop `velo.key` from the content grant. If drafts are SQL, they do not justify fs write of the key. Pin that narrower scope with `toEqual` in the test, independently of main.

HIGH — `src/utils/windowKind.ts` vs `content.json` `"windows"`

```
export function windowKindFromSearch(search: string): WindowKind {
  const params = new URLSearchParams(search);
  if (params.has("thread") && params.has("account")) return "thread";
  if (params.has("compose")) return "compose";
  return "main";
}
export function isPopoutWindow(): boolean {
  return windowKindFromSearch(window.location.search) !== "main";
}
```

```
"windows": ["thread-*", "compose-*"]
```

Before this PR every label had the same 51 permissions, so label vs URL could not change the grant. After, they can disagree:

- Label `main` + `?thread=t&account=a` → `ThreadWindow` (untrusted HTML) with the **full** main grant; pop-out buttons hidden even though create is allowed.
- Label `thread-*` + `/` (no search) → `RouterProvider` (settings, title bar, pop-out buttons) with the **narrow** grant; the buttons then fail closed at `create_webview_window`.

`isPopoutWindow()` never reads `getCurrentWindow().label`. Hiding the two buttons therefore does not mean “this webview lacks create.” It means “this URL looks like a pop-out.”

Fix: derive kind from the Tauri label (`thread-` / `compose-` prefix), use the URL only as a debug assertion. At boot, if label and URL disagree, fail closed (show nothing, log, close). Gate the buttons on the label, not on `location.search`.

MEDIUM — `src/components/composer/Composer.tsx` (close control still mounted) and `content.json` (no `core:window:allow-close` / `allow-start-dragging` / `allow-minimize` / `allow-show` / `allow-set-focus`)

The pop-out create button is gated. The adjacent close control is not:

```

```

`FORBIDDEN_IN_CONTENT` strips `allow-close`, `allow-start-dragging`, `allow-minimize`, `allow-show`, `allow-set-focus` on the claim “TitleBar is main-only; pop-outs have native decorations.” The `WebviewWindow` constructors are not in this diff, so that claim is unverified. Two concrete failures, both invisible to `capabilities.test.ts`:

2. If they have native decorations, the in-app X and the usual post-send close still need a pop-out-aware path. Store-only `closeComposer` leaves an empty husk; `getCurrentWindow().close()` is denied.

Same class of bug for `setFocus` after send if the composer tries to raise main.

Fix: paste the `new WebviewWindow(...)` options into the PR and treat them as part of the grant. Frameless → put back the window-control ids the chrome actually calls (at least `allow-close` and `allow-start-dragging`). Native decorations → hide the in-app X in a compose pop-out and close on send via an explicit, tested `getCurrentWindow().close()` **with** `allow-close`. Do not rely on import analysis of `TitleBar` alone.

MEDIUM — `src-tauri/capabilities/content.json` `http:default` allow list, and `src/config/capabilities.test.ts` `describe.each(["main.json", "content.json"])`

Content copies main’s allow list:

```
{ "url": "http://*" },
{ "url": "http://*/*" },
{ "url": "http://127.0.0.1:*" },
{ "url": "http://127.0.0.1:*/*" },
{ "url": "http://localhost:*" },
{ "url": "http://localhost:*/*" },
{ "url": "https://*" },
{ "url": "https://*/*" }
```

Unsubscribe is arbitrary sender URLs; Ollama is loopback. Unioning them in every email-rendering window means a sanitizer bypass can POST the mailbox (via `sql:default` select) to any https origin **and** hit anything on `127.0.0.1:<any port>` (Ollama, other local services). That was already true when the grant was flat; this PR’s tests now **freeze** that union onto content. `describe.each` with the same URLPattern positives/negatives, plus the comment “it must be the same scope,” makes a later least-privilege split (localhost-only on compose, no world http on content) a test failure.

`opener:default` is the sibling hole: default-urls are not a scheme allow list. Hostile HTML that reaches `openUrl("file://...")` / `smb://` / a custom protocol is an OS-handler problem, not an “email link” problem.

Fix: do not pin identity with main. Pin a **maximum** for content. Prefer a Rust command for unsubscribe (validate http(s), no loopback) and restrict content `http` to the Ollama origin if the composer must keep talking to it. Scope opener to `http`/`https`/`mailto`, or open only through that same command. If the identical world-http list is an accepted residual, say so in the capability description and in an explicit test named as residual, not as “must be the same.”

MEDIUM — `src/config/capabilities.test.ts`

`main.permissions` is exact-equality pinned. Content is not.

```
it("keeps in content windows everything a pop-out calls", () => {
  for (const required of REQUIRED_IN_CONTENT) {
    expect(ids, `${required} is needed by a pop-out`).toContain(required);
  }
});
```

The subset check is `idOf` only. `FORBIDDEN_IN_CONTENT` + `FORBIDDEN_PLUGINS_IN_CONTENT` is a partial blocklist. Together that means:

- Adding any main id that is not on those blocklists (`opener:allow-open-url`, `dialog:allow-save`, `core:window:default`, a new plugin someone also adds to `MAIN_PERMISSIONS` in the same PR) does not go red.
- Widening content’s `http:default` / `fs:scope` **allow arrays** does not go red at the subset test; extra patterns only fail if a SPEC-280 negative URL happens to cover them.
- Narrowing main is caught; narrowing content to something still inside `REQUIRED_IN_CONTENT` (e.g. drop `fs:allow-appdata-write-recursive`, keep `write-file`) is not.

`content.permissions.length < main.permissions.length` is not a ceiling.

Fix: snapshot `content.permissions` with `toEqual` the same way as `MAIN_PERMISSIONS`. Compare `http` and `fs:scope` objects with `toEqual`, per file, with **different** expected values. Add a scan test that `WebviewWindow` / `createWebviewWindow` only appear in the known main-window modules (today: the two pop-out handlers). The JSON tests cannot see runtime deny; that scan at least pins the create path.

LOW — `content.json` still over-grants relative to “demonstrably call”

Even after a cache-only fs scope, these are not required by the story in the description:

- `dialog:default` (includes `allow-open` and `allow-message`, not just save)
- `sql:allow-execute` justified by `runMigrations()` on mount — migrations are a main/startup job; draft auto-save is the real reason execute stays, and it is all-or-nothing at the plugin. Skip migrations in `ThreadWindow` / `ComposerWindow` so the comment stops laundering a startup write into the untrusted window.
- `core:default` includes `emit` / `emit-to`. A bypass can talk to main if main trusts events. Prefer `allow-listen` if the IMAP listener is inbound-only.

Residual, not introduced: `sql:default` (select) + world `http` is still full mailbox exfil. The split’s real savings are create / `fs:remove` / autostart / updater / notifications. Do not describe that as the sanitizer-bypass cost being “less” in any data-confidentiality sense until http is proxied.
