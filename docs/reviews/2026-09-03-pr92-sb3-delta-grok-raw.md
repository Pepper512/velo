**1. Verdict: CHANGES REQUESTED**

Relied on outside this delta: `itemsRef.current` is assigned from `items` during render (same pattern as `virtualizerRef` here); `isLoading` / `items` live in the thread store and do **not** update in the same render as `activeAccountId` / `activeLabel` / `activeCategory`; `loadMore` is referentially stable enough and guards on `hasMore` / `loadingMore` internally; `ListItem.key` / `threadId` / `estimate` are stable and present on thread and bundle-child rows; the pre-existing `scrollTo` stub both writes `scrollTop` and dispatches `scroll` on `.overflow-y-auto`; `renderedRows()` reads `data-thread-id`; `rows` includes `t150` and at least 100 threads; `ROW` matches the estimate the virtualizer uses before measure.

**2. Findings**

**[M] M1 — `src/components/layout/EmailList.tsx`** — The stagger set is captured on the first render where `!isLoading && items.length > 0 && staggerRef.current?.folder !== folderKey`. That is exactly the folder-switch frame this commit is trying to fix: nav has already changed `folderKey`, the previous folder’s rows are still on screen (the new comment says they are), and `isLoading` is still `false` until a later store effect. That frame writes `{ folder: <new key>, keys: Set(<old items’ first 15 keys>) }`, so (a) the outgoing list gets `stagger-in` (keys match those rows) and (b) when the new folder actually loads, `staggerRef.current.folder === folderKey` already, so the set is never rebuilt and the new rows never stagger. The `staggerKeys = staggerRef.current?.folder === folderKey ? … : null` split only helps when capture is skipped (`isLoading === true` on that frame), which this condition does not guarantee. Capture must be keyed to “this folder’s first loaded items,” e.g. invalidate on `folderKey` change without filling keys until `isLoading` has gone true-then-false for that key (or until `items` is known to belong to it). The new test never changes folder, so it cannot catch this.

**[L] L1 — `src/components/layout/EmailList.tsx`** — `selectedPresent` is a boolean, and the effect is `[selectedThreadId, selectedPresent]`. A reload that **reorders** while the selected id stays in `items` does not re-fire (presence stays `true`) — that part of the new comment is right. A reload that **drops then re-adds** the row *does* re-scroll: `selectedPresent` goes `true → false → true`, and the `false → true` transition is the same one used for deep-link/boot. That is acceptable for boot, collapsed-then-expanded bundle children, and filters that hide then show the thread. It is a snap-back if any load path clears `items` while leaving `selectedThreadId` set. The previous invariant (“a reload while the user has scrolled away must not snap back”) was silently narrowed to “merely reorders.” If a clear-and-fill path exists, latch “already scrolled for this id” (reset the latch when `selectedThreadId` changes) instead of using presence as the second key.

**[L] L2 — `src/components/layout/EmailList.virtual.test.tsx`** — The load-more test claims “when the last rendered row is within five of the end” but only does `scroller.scrollTo({ top: 50 * ROW })` and waits for `threads.length === 100`. EmailList does not listen to `scroll`; it reacts to `lastRenderedIndex` from `virtualizer.getVirtualItems()`. A stub that **only** dispatches `scroll` and does not set `scrollTop` leaves the range in the first page (the sibling test asserts `< 40` rows rendered on 200 items, so `lastRenderedIndex` starts well below `items.length - 5`) and this would not exercise the guard. Even with `scrollTop` assigned, `50 * ROW` is “jump to the end of page 1,” not an assertion of the `>= length - 5` predicate (it would also pass for `>= length - 1` or a `loadMore()` on any scroll). The `calledTimes(1)` / `offset 50` checks are the real signal, and they depend on the stub and scroller selector, both outside this delta.

**[L] L3 — `src/components/layout/EmailList.virtual.test.tsx`** — Selection-before-load is a good proxy (`t150` in `renderedRows()` while length `< 40`). The bundle test only checks header-first / `t0` hidden / expand yields two `.pl-4`. Nothing selects a `bundle-child` and asserts it is the scrolled index, which was finding (2) (`kind === "thread"` dropped from `findIndex`). That production change is plausible but unproven.

**[N] N1 — `src/components/layout/EmailList.tsx`** — `selectedPresent` already scans `items`; the effect scans `itemsRef` again. Harmless. Render-time `staggerRef` writes are idempotent on Strict Mode’s double-invoke (same instance), but a discarded concurrent render could leak a `folderKey` into the ref; low practical risk if folder changes are not `startTransition`’d.

**3. Verified-correct**

- Deep link / boot: empty list ⇒ `selectedPresent === false`; after load, presence flips true and `scrollToIndex` runs without putting `items` itself in the dep array, so a reorder does not snap.
- `findIndex((it) => it.threadId === selectedThreadId)` no longer requires `kind === "thread"`, so an expanded bundle child is a valid scroll target once it is in `items`.
- `hasMore` / `loadingMore` on the load-more effect stop the idle `loadMore()` spin once the list is complete; `loadingMore true → false` after a page grow does not immediately chain another page unless the new tail is already inside the last five.
- Missing `threadMap` entries return `<div style={{ height: item.estimate }} />` for both `thread` and `bundle-child`, so the measured node is not 0.
- `buildListItems` records emitted `threadId`s after the bundle loop and skips those ids in the plain-row loop; the new test (`x` as expanded child, `a` as plain) matches that contract.
- Stagger-by-key (once captured) survives a follow-up render, so a virtualizer measure rerender will not strip `stagger-in`; a row whose key was not in that set (`t150`) does not get the class. That part of REQ-3.4 is fixed **for the initial folder only**.
