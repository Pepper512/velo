### 1. [MEDIUM] `src/config/capabilities.test.ts` — `allowed()`

**Concern:** REQ-1.3 asks to pin the plugin’s matcher. The test builds patterns with Node’s `URLPattern`, not the `urlpattern` crate used in `tauri-plugin-http`. Those oracles diverge on omitted pathname and on whether `/*` crosses `/`.

**Input:** `http://127.0.0.1:11434/v1/chat/completions` (the real Ollama OpenAI path: three segments).

**Consequence:** CI can be green on Node while the plugin still refuses before a socket opens (the original bug), or the reverse. The OR over every allow entry also hides *which* pattern matched, so a later edit that turns the no-path patterns into exact `/` can still pass as long as some other entry matches.

**Fix:** Add a Rust test next to the capability file that parses the same `allow` URLs with the same `urlpattern` crate/version as the plugin and asserts this URL. Until then, treat the Node file as a regression net, not as proof the plugin will accept the request.

### 2. [LOW] `src/config/capabilities.test.ts` — REQ-1.2 negatives

**Concern:** Current denies are `http://evil.example:8080/x` and `http://10.0.0.5:11434/v1/models`, plus a string check that no allow URL contains `*:*`. That does not pin “do not open the Local AI ports for every host.”

**Input (should also refuse):**

**Consequence:** An edit such as `{ "url": "http://*:1234/*" }` leaves every existing assertion green and opens LM Studio’s port to the network over plain http. `includes("*:*")` does not catch `http://*:1234`.

**Fix:** Assert those URLs are false. Optionally snapshot the allow list so extra hosts/ports cannot sneak in.

### 3. [LOW] `src/services/ai/errors.ts` — `describeError` → `SettingsPage` (both AI cards)

**Concern:** REQ-2.4 assumes SDK / plugin strings never carry credentials. `describeError` returns `err.message` or `String(err)` with no redaction. OpenAI-compatible `APIError.message` is commonly `Incorrect API key provided: sk-…`. Gemini puts the key in the query string; a scope-refusal or fetch error that embeds the URL would show `key=`. The settings catch path duplicates this (`err.message` / `String(err)`).

**Input:** `testConnection` rejects with `new Error("Incorrect API key provided: sk-live-SECRET")`, or a plugin string `url not allowed on the configured scope: https://generativelanguage.googleapis.com/v1beta/models/x:generateContent?key=SECRET`.

**Consequence:** The key (or a prefix/suffix) is rendered next to “Connection failed” and in `title=`. React text is not XSS; it is a display leak. The settings field already has the key, so this is shoulder-surf / screenshot, not a new store of secrets.

**Fix:** Redact `sk-`, `ghp_`, `xai-`, `AIza`, `Bearer `, and `key=` / `api_key=` query values before display. Prefer status-stable copy for 401/403 (“Invalid API key”) as Gemini already does on 401.
