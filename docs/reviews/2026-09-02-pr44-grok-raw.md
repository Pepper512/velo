**CHANGES REQUESTED** — the timeout path returns `Ok` after the session is desynchronised, so the pool’s `Err`-path eviction the comment relies on does not run, and `checked: true` is both documented and set in cases where no UID SEARCH completed; either one lets part 2 treat a bad or skipped observation as a complete pass.

## Findings

1. **HIGH** — `src-tauri/src/imap/client.rs` (`delta_check_folders`)
   - **Concern:** SELECT/UID SEARCH timeout returns `Ok(results)` after explicitly stating the session is desynchronised and that “the caller’s `Err` path evicts it.”
   - **Trigger:** Any `with_timeout` `Err` on SELECT or UID SEARCH. The function pushes `unchecked`, `mark_rest_unchecked`s the tail, and `return Ok(results)`.
   - **Consequence:** The connection is left mid-command (response may still arrive). If `withSession` / the pool recycle on `Ok` and evict only on `Err`, the next user of that session — including part 2’s `UID SEARCH ALL` — can consume a leftover or truncated payload as a well-formed UID list. Two such “passes” satisfy the state machine and delete real mail. REQ-3.3 (timed-out SEARCH deletes nothing) is only as strong as “this session is dead.”
   - **Suggested fix:** Keep the per-folder `unchecked` rows (REQ-1.2b needs a total function), but do not return this session to the pool. Either return `Err` after the session is disconnected, or return `Ok` **and** evict/drop the session on this path (a dedicated “poisoned” outcome). Update the comment so it matches the control flow. Add a test that the command/handler error path is the one the pool actually uses.

2. **MEDIUM** — `src-tauri/src/imap/types.rs` + `client.rs` UIDVALIDITY branch
   - **Concern:** `checked` is documented as “`true` only if SELECT and the UID SEARCH both completed,” but the UIDVALIDITY-changed arm sets `checked: true` with `new_uids: []` and **does not SEARCH**. The SEARCH this function runs is also the delta `last_uid+1:*` search, not `UID SEARCH ALL`.
   - **Trigger:** `req.uidvalidity != 0 && current != req`. Part 2 later uses `r.checked` as “this folder was fully listed.”
   - **Consequence:** A pass can look attested-complete with no `UID SEARCH ALL` on that folder. That does not delete by itself (part 1 doesn’t delete), but it trains part 2 to treat `DeltaCheckResult.checked` as REQ-1.2(a)/(b). Existing TS already skips `!checked` and then branches on `uidvalidity_changed`, so flipping this flag to `false` would also skip the current UIDVALIDITY resync — the flag is overloaded.
   - **Suggested fix:** Leave `checked` meaning “delta-check SELECT produced a usable row” (so UIDVALIDITY handling keeps working). Delete the “UID SEARCH both completed” sentence. Give part 2 a **separate** predicate for “`UID SEARCH ALL` actually ran this pass in folder F” (the `imapSearchAllUids` success, not `delta.checked`). Do not let pass attestation be `deltaResults.every(r => r.checked)`.

3. **MEDIUM** — `src/services/imap/imapSync.ts` fallback path
   - **Concern:** Batch `delta_check_folders` now returns a row for every requested folder. The per-folder fallback (batch `catch`) still only writes the map on success; the `folderErr` arm is unchanged, so failed folders are **omitted**, which is the pre-F-4 bug.
   - **Trigger:** Batch delta check throws (including a future timeout-as-`Err` fix). Fallback STATUS/SEARCH fails for folder N of M.
   - **Consequence:** `deltaResultMap` is not a total function of `syncableFolders`. Part 2 attestation written as ` [...map.values()].every(r => r.checked)` or `checked.length === deltaResults.length` will look clean while N folders were never checked — exactly the silent-omission failure REQ-1.2b exists to prevent. The new `if (!deltaResult || !deltaResult.checked) continue` is safe for **skipping work**, not for **attesting completeness**.
   - **Suggested fix:** On fallback `folderErr`, `deltaResultMap.set(folder, { folder, checked: false, error: String(folderErr), exists: 0, new_uids: [], uidvalidity: saved, uidvalidity_changed: false })`. Part 2 must attest `checkedSet == syncableFolderSet`, treating a missing map entry as failure, never as “not in the result so ignore.”

4. **MEDIUM** — `src/services/imap/reconcile.ts` (`confirmedOnPass` / `recordMissing`)
   - **Concern:** The deletion set is not generation-scoped, and `recordMissing` re-stamps **any** row with `first_pass_id <> passId`, including stale `confirmed_absent` rows. REQ-1.5’s end-of-pass filter is only `status = confirmed_absent AND last_verified_pass_id = N`.
   - **Trigger (generation):** Part 2 calls `confirmedOnPass` without `purgeOtherGenerations` first; an old-generation confirmed row that somehow shares pass id N is returned. **Trigger (resurrection):** Pass 1–2 confirm UID 5; pass 3 it reappears and part 2 forgets `clearReappeared`; pass 4 it vanishes once; `first_pass_id` is still pass 1, so the UPDATE re-stamps `last_verified_pass_id = pass-4` and `confirmedOnPass(pass-4)` yields it — **one new observation deletes**.
   - **Consequence:** Two-pass confirmation and UIDVALIDITY isolation become caller-optional. That is the obvious way part 2 deletes on a single observation or shoots a regenerated mailbox.
   - **Suggested fix:** `confirmedOnPass(accountId, folder, uidvalidity, passId)` must include `AND uidvalidity = $n`. Export one atomic `applySearchAll({ presentUids, missing, currentUidvalidity, passId })` that `purgeOtherGenerations` → `clearReappeared` → `recordMissing` in one `withTransaction`. Make calling the pieces separately the unusual path, not the default. Document as a hard invariant: every successful `UID SEARCH ALL` must run the trio; a skipped gate / folder error must call none of them.

5. **MEDIUM** — `src/services/imap/reconcile.ts` (`recordMissing`)
   - **Concern:** Promote UPDATE and the per-UID `INSERT OR IGNORE`s are separate auto-committed statements; `withTransaction` is unused. Re-stamping already-confirmed rows is the right reading of REQ-1.5 (budget leftovers would otherwise be stuck on the old `last_verified_pass_id` and never enter `confirmedOnPass(N)`), but it is not atomic with the inserts.
   - **Trigger:** Crash / `execute` failure mid-chunk; two overlapping syncs for the same folder.
   - **Consequence:** Partial promote without the new suspects (fail-toward-keep, acceptable) or two pass ids interleaved on the same UID. Desktop probably serializes sync; the harness cannot see the gap. Part 2 will read `confirmedOnPass` in the same turn, so this is mostly crash-safety.
   - **Suggested fix:** Wrap each chunk (or the whole call) in `withTransaction`. Keep promote-then-insert and `first_pass_id <> passId` — that ordering is correct for same-pass double report, pass-1 then pass-3 with pass-2 skipped, and re-stamping leftovers.

6. **LOW** — `src/services/db/migrations.ts` (`first_seen_at`)
   - **Concern:** `first_seen_at INTEGER DEFAULT (unixepoch())` is nullable, second resolution. `confirmedOnPass` orders `first_seen_at ASC, uid ASC`.
   - **Trigger:** Many suspects inserted in the same second (normal); a row inserted with explicit NULL.
   - **Consequence:** “Oldest first” (REQ-3.1) becomes UID order for a whole second. Not data loss; batching is slightly arbitrary. SQLite `ORDER BY` NULLS-first can put a NULL ahead of real timestamps.
   - **Suggested fix:** `first_seen_at INTEGER NOT NULL DEFAULT (unixepoch())`. If fairness across a burst matters, use a monotonic counter or `unixepoch('subsec')` if the bundled SQLite is new enough. Tie-break by `uid` is fine once NOT NULL.

7. **LOW** — `src-tauri/src/imap/types.rs` (`DeltaCheckResult::unchecked`)
   - **Concern:** `exists: 0` on every unchecked row. Comment says the row “carries nothing the caller could mistake for an observation,” but `exists: 0` **is** an observation of an empty mailbox.
   - **Trigger:** Part 2 REQ-2.1 gate uses `exists` without `checked`.
   - **Consequence:** `0 !== local_count + flagged_not_expunged` looks like “folder emptied,” which is the SEARCH-ALL trigger, on a folder that was never SELECTed. Extra SEARCH is the safe direction only if the session is healthy (see finding 1).
   - **Suggested fix:** Keep `exists` meaningful only when `checked` (and SELECT succeeded). Option `<u32>` / TS `number | null` for unchecked rows, or assert in the gate. Do not send `0` as a sentinel.

8. **LOW** — `src/services/imap/reconcile.ts` (`planDeletions`)
   - **Concern:** The >50% stop is `localRows > 10 && confirmedCount * 2 > localRows`. For `localRows <= 10` (including 0 or a miscounted empty folder) the floor cap is 10 and the stop never fires.
   - **Trigger:** `planDeletions(0, 8)` → `{ budget: 8, stop: false }`; `planDeletions(5, 8)` → budget 8 against 5 local rows.
   - **Consequence:** Spec-allowed for real ≤10 folders; a bad `localRows` query bypasses the human stop and asks part 2 to delete more IDs than the folder has. Not a part-1 delete, but the budget API will not save a wrong count.
   - **Suggested fix:** Clamp `localRows` to `>= 0`. Optionally `budget = min(cap, confirmedCount, max(localRows, 0))`. Guard `localRows === 0 && confirmedCount > 0` as stop or budget 0 (inconsistent inputs). Test `planDeletions(0, n)`.

9. **NIT** — `src-tauri/src/imap/client.rs` tests
   - **Concern:** The new test only drives `mark_rest_unchecked`, and it passes the **full** request list as `rest`, plus a pre-canned Archive row. It does not lock `folders[idx..]` (timed-out folder excluded) or the SELECT-fail continue-vs-timeout-abandon split.
   - **Trigger:** Off-by-one on `idx += 1` before `folders[idx..]`.
   - **Consequence:** A duplicate row for the timed-out folder would not be caught; TS `Map` would keep the last. Unchecked duplicate is still fail-toward-keep.
   - **Suggested fix:** One table-driven test of the slice contract: timeout at index i ⇒ results length == folders.len(), `results[i].folder` is the timed-out one, `results[i+1..]` match `folders[i+1..]`.

10. **NIT** — `src/services/imap/reconcile.test.ts`
    - **Concern:** No test that a `confirmed_absent` leftover (budget-capped, still missing) is re-stamped on the next search and appears in `confirmedOnPass(next)`. No test that `recordMissing` on an already-confirmed UID that is **not** in this pass’s missing list leaves `last_verified_pass_id` unchanged.
    - **Trigger:** Part 2 implements REQ-3.1 leftovers.
    - **Consequence:** The re-stamp behavior is load-bearing and only implied by the unfiltered UPDATE.
    - **Suggested fix:** Add those two harness cases before part 2.

11. **NIT** — `src/services/db/migrations.ts`
    - **Concern:** No `CHECK (status IN ('suspect','confirmed_absent'))`; `first_pass_id` / `last_verified_pass_id` are unconstrained TEXT. Index `(account_id, status, last_verified_pass_id)` omits `folder`, which `confirmedOnPass` filters on.
    - **Suggested fix:** CHECK constraint; include `folder` in the index if part 2 will call this every pass.

## Questions the author should answer

1. After a SELECT/SEARCH **timeout**, does the session-pool evict on any non-success, or only on `Err`? What is the exact `withSession` / `imapDeltaCheck` contract? The comment and the `Ok` return cannot both be right.
2. Confirm part 2 will **not** use `DeltaCheckResult.checked` as “`UID SEARCH ALL` ran.” What is the planned attestation expression? It must be `checkedFolders == syncableFolders` with omitted fallback entries counted as failures, plus a per-folder “SEARCH ALL succeeded this pass” bit.
3. Is `passId` stable for the whole account pass (every folder, every `recordMissing` in that sync)? If part 2 mints a new id per `recordMissing` call, a single SEARCH ALL reported twice will promote on the second call and collapse REQ-1.2(a).
4. Will every successful `UID SEARCH ALL` always invoke `purgeOtherGenerations` + `clearReappeared(present)` + `recordMissing(absent)` together, including when `present` is empty (empty folder — `clearReappeared` currently no-ops on `[]`, which is correct) and when `missing` is empty?
5. Does the migration runner execute **all three** statements in version 26 (`CREATE TABLE`, `CREATE INDEX`, `ALTER TABLE`)? The harness test should fail if `ALTER` is dropped, but only if it actually runs this migration as a multi-statement script.
6. What is `isUid`? The new tests lock out `0`, `1.5`, and `"5"`; is `NaN`, negative, `2^32`, and `Number.MAX_SAFE_INTEGER + 1` rejected too?
7. For a UIDVALIDITY-changed folder, is `exists` from SELECT intended as REQ-2.1 gate input for that same pass, or is the folder forced to full resync (gate irrelevant)? The row currently looks like a successful check.
8. Re-stamping `last_verified_pass_id` on already-confirmed rows: please state in the module comment that this is **required** for REQ-3.1 leftovers, not an accident. The spec text only mentions promoting *suspects*; the budget does not work without the re-stamp.

## What is good

- Part 1 does not delete `messages` rows. Suspect table mutations are advisory; `forgetSuspects` / `clearReappeared` / `purgeOtherGenerations` only touch `reconcile_suspects`.
- REQ-1.2b’s actual bug is fixed on the batch path: SELECT failure and UID SEARCH failure no longer look like “checked, no new UIDs.” SEARCH failure previously returned `vec![]` and continued; that silent empty observation is gone.
- `DeltaCheckResult::unchecked` zeros `new_uids` and `uidvalidity_changed`. `imapDeltaSync` skipping `!checked` is the conservative default for existing delta-fetch.
- `imapSearchAllUids` distinguishes a valid empty folder (`[]`) from a malformed payload (`null`, non-array, UID 0, non-integer, string entry) and throws — an empty list is no longer the error representation.
- `recordMissing` promote-then-insert with `first_pass_id <> passId` is the right state machine: same-pass double report stays `suspect`; pass 1 then pass 3 with pass 2 skipped promotes; new UIDs on the later pass insert as `suspect`; `INSERT OR IGNORE` cannot demote. Re-stamping confirmed rows is what makes `confirmedOnPass(N)` see budget leftovers. `$n` used once, ascending, with pass id bound twice, matches the harness translator.
- `planDeletions` is a budget, not a precondition: 15 over a cap of 10 yields 10; the >50% stop is strict majority (`* 2 >`) and does not fire at exactly 50%; ≤10-row full clear is implemented as specified; `deletionCap` matches `min(500, max(10, ceil(10%)))`.
- `clearReappeared([])` is a no-op — an empty server list cannot clear suspects. Folder-error tests correctly call nothing. PK includes `uidvalidity`. `flagged_not_expunged INTEGER NOT NULL DEFAULT 0` is the valid SQLite `ALTER TABLE` form (constant default backfills existing rows).
- Tests hit the load-bearing cases (first sight is never confirmed, same-pass no promote, later-pass promote, skip does not age, reappear clears any status, generation purge, per-folder key, oldest-first order). No new dependencies. Commit-message claims about the new fields, `unchecked`, per-folder reporting, TS skip/warn/count, fallback success fields, migration 26, and the `reconcile.ts` API match the diff — except the timeout path’s implied eviction, which the comment claims and the `Ok` return does not do.
