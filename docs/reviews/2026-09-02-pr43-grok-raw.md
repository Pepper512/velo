## Findings

1. **HIGH** — `src/services/db/messages.ts` (`reapMovedTombstones`), called from `upsertMessage`  
   **Concern:** The DELETE is keyed only on `(account_id, message_id_header)` plus `moved_to IS NOT NULL`. Message-ID is not a per-folder identity; it is shared by every IMAP copy of the same RFC 5322 message (Sent + INBOX, INBOX + a filter-copied folder, two moves of two copies).  
   **Trigger:** Two local rows share `<a@example.com>`. Both are moved without a usable COPYUID (or one mapped row is skipped for collision) so both are tombstoned, possibly to *different* destinations. The first destination folder upserts a row with that header.  
   **Consequence:** Every tombstone with that header is deleted, including one whose destination has not been synced. Attachments cascade. The only cached body/parts for the second copy are gone until that other folder happens to sync — and if the user never opens it, they stay gone. A tombstone that landed in a different `thread_id` (duplicate/broken Message-IDs) is deleted from that thread the same way.  
   **Fix:** Reap only rows that were waiting for *this* arrival, e.g. `AND moved_to = $imapFolder` (and, if you store it, the dest UID). Do not delete tombstones aimed at another folder. Add a harness case: INBOX copy archived and Sent copy moved to Projects, then Archive upsert must not delete the Projects tombstone.

2. **HIGH** — `src/services/imap/moveHygiene.ts` (`settleMovedRows`) + `src/services/db/messages.ts` (`tombstoneMovedMessages` / `reapMovedTombstones`) + `src/services/email/imapSmtpProvider.ts`  
   **Concern:** Fallback rows keep their *source* `id` / `imap_folder` / `imap_uid`. `settleMovedRows` is not given `expunged` and always tombstones the same way for `mapping === null`.  
   **Trigger A (source sync wins):** UID MOVE/COPY with no COPYUID → tombstone still named `imap-{acc}-INBOX-{uid}`. The next INBOX reconciliation removes UIDs the server no longer lists (MOVE, or a later expunge). That DELETE is the tombstone. Archive has not been selected yet.  
   **Trigger B (COPY fallback, live `:11144` shape):** `MoveResult { expunged: false, mapping: None }` — source copy still on the server, `\Deleted`. Dest sync inserts a fresh id and `reapMovedTombstones` deletes the source row. The next INBOX sync fetches the still-present UID and **inserts it again**.  
   **Consequence:** A: cached body/attachments disappear until dest sync (Done-when 2 never runs: there is nothing left to reap). B: the original double-row / double-render defect comes back on the no-UIDPLUS path the brief called out. Print/.eml follow `getMessagesForThread`, so they duplicate again too.  
   **Fix:** Pass `expunged` into `settleMovedRows`. If the source UID is still live, do not reap on dest upsert; reap (or delete) when the *source* folder reports that UID gone. Exclude `moved_to IS NOT NULL` from vanished-UID cleanup so a hidden row can survive until dest arrival. Optionally park fallback rows under a non-folder id so INBOX sync cannot own them.

3. **HIGH** — `src/services/db/messages.ts` (`getMessagesForThread` only) + migration 25  
   **Concern:** The brief’s hidden-row semantics are “hidden from actions **and lists**.” The diff filters `moved_to IS NULL` in one SELECT. Folder listings, search/FTS, unread/star counts, and any other `SELECT * FROM messages` are unchanged. FTS is still maintained for the tombstone (`moveHygiene.test.ts` even checks the index still matches).  
   **Trigger:** No-UIDPLUS archive of an INBOX message; user is still looking at INBOX, search, or a count badge, not the thread view.  
   **Consequence:** Ghosts remain in the source folder and in search. Acting on them hits `keepLiveMessageIds`, which drops the id and succeeds as a no-op — the message looks live and is not. Done-when 2 is only true for thread listing and provider actions, not “lists.”  
   **Fix:** Make `moved_to IS NULL` a single helper/view used by every user-facing message query (folder list, search, counts, export paths that do not go through `getMessagesForThread`). Add harness coverage for a folder list query, not only `getMessagesForThread`.

4. **MEDIUM** — `src/services/imap/messageHelper.ts` (`keepLiveMessageIds`) + `src/services/email/imapSmtpProvider.ts` (`groupLiveByFolder`)  
   **Concern:** Stale ids are dropped with a `console.warn` and the action still resolves. There is no old→new alias after a successful re-key.  
   **Trigger:** UIDPLUS archive re-keys `imap-acc-INBOX-100` → `imap-acc-Archive-7`. React selection, an undo stack, a retry, or any offline queue still holds the old id. User stars / mark-read / delete immediately after archive.  
   **Consequence:** `keepLiveMessageIds` returns `[]` (or a subset). `markRead`/`star`/`permanentDelete` never touch the server. The UI can report success. This is safer than targeting the wrong UID, but it silently drops legitimate work the old id still named. Search hits that still expose tombstoned ids fail the same way (finding 3).  
   **Fix:** After re-key, either (a) return the new ids to the caller and have the UI/queue rewrite them, or (b) resolve live ids in SQL (`id IN (…) OR id IN (rewritten form)` — you would need a durable alias to do (b)). If every submitted id is dropped, fail the action instead of resolving.

5. **MEDIUM** — `src/services/db/messages.ts` (`rekeyMovedMessages`, `PRAGMA defer_foreign_keys = ON`)  
   **Concern:** Deferral is required: there is no statement order that changes `messages.id` under `attachments(account_id, message_id)` without an immediate FK check. `PRAGMA defer_foreign_keys` is per-connection and is reset at the start of the next transaction. Production is sqlx via tauri-plugin-sql (typically a pool). The harness reimplements `withTransaction` on one `better-sqlite3` handle, so it cannot catch a pooled `execute` landing the PRAGMA on a different connection than the UPDATEs.  
   **Trigger:** Re-key a moved message that has attachments, in production.  
   **Consequence:** If the PRAGMA does not apply to the writer connection, the `UPDATE messages SET id = …` fails the FK, the transaction rolls back, `settleMovedRows` tombstones instead. Option A silently never runs for any message with attachments; those rows take the Option B hazards in findings 1–3. Attachment-less rows would still re-key, so the failure is easy to miss.  
   **Fix:** Prove `withTransaction` pins one connection for BEGIN + PRAGMA + DML + COMMIT (or use `IMMEDIATE` and a dedicated connection). Add a production-path test, not only the harness mock. If PRAGMA cannot be relied on, copy to a new `(account_id, id)` row, move children, delete the old row, in one transaction.

6. **MEDIUM** — `src/services/db/messages.ts` (`rekeyMovedMessages` pre-check SELECT then UPDATE)  
   **Concern:** The “taken” SELECT is not a lock. SQLite DEFERRED transactions take the write lock on the first *write*; a concurrent `upsertMessage` (not using `withTransaction`) can INSERT the dest id after the SELECT and before the UPDATE. The comment admits this; the backstop is the composite PK.  
   **Trigger:** Dest folder sync inserts `imap-{acc}-Archive-3` while a COPYUID re-key of that same new id is in flight.  
   **Consequence:** PK fails, **the whole batch** rolls back (tested), then `settleMovedRows` tombstones *every* UID in the move, including ones that had no collision. A 200-message archive becomes 200 Option B rows because one dest UID raced. Data is not overwritten (good), but Option A is abandoned for the batch.  
   **Fix:** `BEGIN IMMEDIATE` (or `EXCLUSIVE`) so the pre-check cannot race; on PK collision, skip/tombstone only the colliding pair instead of aborting the transaction (savepoints per pair, or apply one-by-one after an immediate lock).

7. **MEDIUM** — `src/services/email/imapSmtpProvider.ts` (`noticeIfNotExpunged` then `settleMovedRows`)  
   **Concern:** Local settlement runs only if the provider gets a successful `MoveResult` *and* the notice call returns.  
   **Trigger:** Server MOVE succeeded (and may have expunged), but `imapMoveMessages` throws (timeout, pool eviction, IPC) or `noticeIfNotExpunged` throws.  
   **Consequence:** `settleMovedRows` never runs. Local ids still name source folder/UID. Retry of a COPY fallback can duplicate mail (the comment in `moveHygiene.ts` is exactly this hazard). Timeout-after-success is older than F-5, but now the mapping is also lost.  
   **Fix:** `try / finally` around notice vs settle (settle even if notice fails). Treat “MOVE completed, drain failed” as `mapping: null` rather than a thrown move. Persist an intent to settle before the IMAP command if you have a queue.

8. **LOW** — `src-tauri/src/imap/copyuid.rs` (`expand` on `UidRange`)  
   **Concern:** Reversed ranges are normalized with `min`/`max` before positional zip. RFC 4315 COPYUID sets correspond *in order*; RFC 3501 unordered-set language does not apply to that pairing.  
   **Trigger:** Server sends `COPYUID … 7:5 10:12` meaning 7→10, 6→11, 5→12.  
   **Consequence:** Local mapping becomes 5→10, 6→11, 7→12. Rows re-key to the wrong dest UIDs. Next dest sync then overwrites those ids with whatever the server actually has there. The test `a_reversed_range_is_the_same_set` locks in the wrong pairing when only one side is reversed (both sides reversed happens to cancel).  
   **Fix:** Expand a range in the order it was written (`start` toward `end`), not sorted. Keep the empty-`RangeInclusive` guard, but iterate with a signed step.

9. **LOW** — `src-tauri/src/imap/copyuid.rs` (`mapping_from_response` ignores COPYUID uidvalidity)  
   **Concern:** Dest UIDs are only meaningful for that mailbox generation.  
   **Trigger:** COPYUID uidvalidity does not match the dest folder’s current UIDVALIDITY (stale unsolicited, or a folder that was recreated).  
   **Consequence:** Re-key onto UIDs that now belong to other messages, or to UIDs that do not exist. Collision skip/PK rollback covers some cases; a free dest id does not. Next sync may correct, but you can attach local flags/body to the wrong dest identity until then.  
   **Fix:** Compare COPYUID uidvalidity to the dest folder’s last known value if you store it; otherwise refuse the mapping (`None` → Option B) when you cannot.

10. **LOW** — `src-tauri/src/imap/client.rs` (`discard_pending` before `UID MOVE`, then `drain_copyuid`)

    **Trigger:** New mail or a delayed untagged COPYUID between discard and MOVE; or a future IDLE/sync consumer of the same pooled session.

## What is good

- Owning no COPYUID parser: `imap-proto`’s `ResponseCode::CopyUid`, a hard cap before iterating `1:4294967295`, mismatched/empty/zero/duplicate-source → `None`, never a panic or a partial map.
- Drain happens **inside** the pooled checkout; the comment about not reading the channel after `release_ok` is correct.
- IPC `parseUidMapping` is fail-closed for the whole map; `null` vs `[]` is preserved.
- `settleMovedRows` cannot fail the IMAP move (no COPY-fallback retry storm from a local SQLite error).
- Re-key is one transaction, `thread_id` left alone (pins/labels/snoozes), attachments’ FK *and* `${messageId}_${part}` PK rewritten so dest sync can hit, collision does not overwrite an existing dest row.
- Harness tests are the right kind: real migrations, `foreign_keys=ON`, FTS trigger, PK rollback, settle-degrades-to-tombstone.
- `keepLiveMessageIds` is the right idea for the original wrong-folder/UID action bug; empty-UID `Some([])` vs absent mapping is a real distinction.
- COPY fallback not inventing a mapping by bypassing `uid_copy` matches the approved wire freeze.
