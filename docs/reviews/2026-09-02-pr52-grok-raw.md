**APPROVE WITH NITS**

Velo-shaped input (`Bcc:` / `Bcc :` on one line, value folding, CRLF or LF, then `\r\n\r\n` / `\n\n`) is stripped, the envelope still carries the blind recipients, and a parser-visible leftover `Bcc` with parseable addresses is refused. Remaining issues are downstream/raw-byte edges, a guard that is narrower than “field present,” and tests that never prove the guard is wired into `prepare_for_wire`.

---

1. **MEDIUM** — `src-tauri/src/smtp/client.rs` `is_bcc_field` / `strip_bcc_header`

   The scanner only treats a *physical* line as `Bcc` if it contains a `:`. A name folded before the colon is kept, including its continuations.

   **Input:**
   ```
   From: alice@example.com\r\nTo: bob@example.com\r\nBcc\r\n : secret@example.com\r\nSubject: Test\r\n\r\nBody
   ```

   **Consequence:** Bytes still contain a `Bcc` field. If `mail_parser` unfolds then parses addresses, `prepare_for_wire` refuses (no leak, cannot send). If it stores the field but `bcc()` is `None` (see 3), the field goes out.

   **Fix:** Unfold as you scan (or treat a non-continuation line whose trimmed bytes are `bcc` with no `:` as the start of a `Bcc` field and drop it plus following `SP`/`HTAB` lines). Add that input as a test.

2. **LOW** — `strip_bcc_header` / `is_bcc_field`

   Fields not literally named `Bcc` are left on the wire.

   **Input:** `Resent-Bcc: secret@example.com\r\n` (also `Bcc (obs): secret@example.com\r\n`, and a leading UTF-8 BOM on the first header: `\xEF\xBB\xBFBcc: secret@example.com\r\n`).

   **Consequence:** `Resent-Bcc` is a definite disclosure on resend. BOM/`Bcc (obs):` leak only if the receiver’s parser is looser than this scanner *and* `mail_parser.bcc()` is `None` (otherwise refuse).

   **Fix:** Strip `Resent-Bcc` the same way if this client can emit or round-trip it; skip one leading UTF-8 BOM before the first field; do not try to parse comments in field names (RFC 5322 `ftext` makes `Bcc (obs)` a different name).

3. **MEDIUM** — `refuse_if_bcc`

   REQ-1.4 is implemented as `message.bcc().is_some()`. In `mail_parser` that is the parsed address list, not “a `Bcc` field exists.” Empty or unparsed values are often `HeaderValue::Text` / `Empty`, so `bcc()` is `None` while the header is still in the raw list.

   **Input (scanner miss + likely guard miss):**
   ```
   From: a@x.org\r\nTo: b@x.org\r\nBcc\r\n : @\r\n\r\nBody
   ```
   **Input (stripped already — guard not at issue):** `Bcc:\r\n` is removed by the scanner; this hole matters only after a miss.

   **Consequence:** Fail-closed can let a `Bcc` field through. It can also refuse a legitimate send when the scanner misses a parseable `Bcc` (finding 1) even though stripping would have been enough.

   **Fix:** Fail if any header’s name is `Bcc` (raw `headers()` / `HeaderName::Bcc`), regardless of address parse. Keep `bcc()` as an extra check if you want.

4. **LOW** — `lines_inclusive` / `header_block_end`

   Lines split only on `\n`. Bare CR is not a line break. The header/body cut is only `\r\n\r\n` or `\n\n`, not mixed `\n\r\n`.

   **Input (CR-only headers):** `From: a@x.org\rBcc: secret@example.com\rTo: b@x.org\r\rBody`

   **Consequence:** One “line,” first `:` is `From`, `Bcc` not stripped. `mail_parser` usually *does* split on CR → refuse, not leak. Spec did not require bare CR.

   **Fix:** Split on CRLF / LF / CR (CR not part of CRLF). Optional; only needed if `send_raw_email` is a public raw-byte API.

5. **MEDIUM** — `header_block_end` / `strip_bcc_header`

   If the real header/body separator is not recognized, the whole message is scanned as headers and a body line `Bcc:` is deleted (REQ-1.3).

   **Input:**
   ```
   From: a@x.org\nTo: b@x.org\n\r\nBcc: not-a-header@x.org\n
   ```
   (LF headers, CRLF blank line, body starts with `Bcc:`.)

   **Consequence:** Body line removed; MIME/quoted content can be damaged. Velo’s builder emits CRLF + `\r\n\r\n`, so this is mixed-ending / downstream.

   **Fix:** Detect the separator as an empty *line* (`""` / `"\r"` / `"\n"` / `"\r\n"`) while iterating, and stop. Do not byte-search `\n\n` inside a `\r\n` + `\n` pair without also treating `\n\r\n` as a blank line.

6. **LOW** — `strip_bcc_header`

   First line starting with WSP is always a continuation (`skipping` stays `false`).

   **Input:** ` Bcc: secret@example.com\r\nFrom: a@x.org\r\n\r\nBody`

   **Consequence:** Line kept. Strict RFC 5322 does not treat it as a field; a parser that trims the first line might. Guard fires only if `mail_parser` treats it as `Bcc`.

   **Fix:** If `body_at > 0` and the first line is WSP-prefixed *and* `is_bcc_field(trimmed)`, drop it and its continuations.

7. **NIT** — `is_bcc_field`

   `trim_ascii_end` is wider than RFC `WSP` (also CR/LF/FF). `bcc\x0c:` is treated as `Bcc` and removed. Illegal field name; harmless over-strip.

8. **Envelope — no defect on the production shape.** `extract_envelope(raw)` runs before strip; `send_raw` gets that envelope. Blind recipients still receive.

   Untested (see 9): Bcc-only (no To/Cc); folded Bcc value list must still all be in `envelope.to()`.

**What is good**

- Envelope from the original bytes, strip only on the SMTP path, Sent/Drafts bytes unchanged (pinned at the TS seam).
- Header-block bound: first `\r\n\r\n` or `\n\n`; body, `Cc`, `X-Bcc-Note`, `Bcc-Ish`, and folded `Subject` continuations that start with `Bcc:` are left intact.
- Byte-for-byte copy of kept lines (CRLF vs LF preserved).
- Case-insensitive name, same-line obs-WSP before `:`, empty `Bcc:`, multiple consecutive `Bcc`s, value folding with SP/HTAB, header-only / empty input.
- Fail-closed idea is right; `send_raw_email` is one path: decode → envelope → strip → guard → `send_raw`.
