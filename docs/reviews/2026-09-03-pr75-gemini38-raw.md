## Independent Code Review: PR #75 — "P11 — split the Tauri capability grant"

### Summary
PR #75 attempts to split Tauri v2 capabilities between `main` (the full 51-permission grant) and pop-out content windows (`thread-*`, `compose-*`, restricted to 14 permissions) to mitigate blast radius in the event of an email sanitizer bypass. 

While the reduction of window-creation, notifications, updater, and system commands is a step in the right direction, the implementation introduces critical runtime defects and leaves severe security vulnerabilities open in the untrusted content windows. Most notably:
1. The HTTP grant in `content.json` retains unrestricted wildcard access to localhost and 127.0.0.1 (bypassing browser CORS via Tauri's HTTP plugin).
2. The filesystem scope restricts writes strictly to `$APPDATA`, which will break user attachment saving and `.eml` exports to user-selected paths (`Downloads`, `Desktop`, etc.) at runtime.
3. Window identity and capability gating rely on mutable URL search parameters rather than immutable Tauri window labels.
4. Stripping `core:window:allow-close` breaks in-app pop-out close controls.

---

### Findings

#### 1. Wildcard HTTP scope exposes loopback services to SSRF and data exfiltration without CORS
- **Severity**: HIGH
- **File**: `src-tauri/capabilities/content.json`
- **Exact Code**:
  ```json
    {
      "identifier": "http:default",
      "allow": [
        { "url": "http://*" },
        { "url": "http://*/*" },
        { "url": "http://127.0.0.1:*" },
        { "url": "http://127.0.0.1:*/*" },
        { "url": "http://localhost:*" },
        { "url": "http://localhost:*/*" },
        { "url": "https://*" },
        { "url": "https://*/*" }
      ]
    }
  ```
- **Why it is wrong**:
  The primary objective of SPEC-P11 is sandboxing untrusted email rendering so that a sanitizer bypass cannot compromise the host. However, `content.json` grants identical wildcard HTTP permissions as `main.json`, explicitly permitting connections to `http://localhost:*` and `http://127.0.0.1:*` on any port. 
  In Tauri v2, `@tauri-apps/plugin-http` executes requests via Rust (`reqwest`) and **bypasses browser CORS entirely**. An attacker who bypasses the email sanitizer inside `thread-*` or `compose-*` can:
  1. Attack local daemons and services running on the machine (Ollama, local databases, internal HTTP APIs, cloud metadata endpoints) via unauthenticated loopback requests.
  2. Exfiltrate SQLite database contents (accessible via `sql:default` and `sql:allow-execute`) or `$APPDATA/velo.key` (accessible via `fs:allow-read-file`) directly to any arbitrary external domain.
  The stated rationale in the PR is supporting Ollama (default port 11434) and the `List-Unsubscribe` POST. Granting arbitrary loopback ports and wildcard plaintext HTTP completely undermines the sandbox.
- **Concrete Fix**:
  Narrow `http:default` in `content.json`:
  1. Restrict Ollama strictly to its designated port: `http://localhost:11434/*` and `http://127.0.0.1:11434/*`.
  2. Remove all wildcard `http://*` and loopback wildcards (`http://localhost:*`, `http://127.0.0.1:*`).
  3. Move the `List-Unsubscribe` HTTP request into a dedicated Rust command (`#[tauri::command]`) that validates URLs backend-side. This avoids exposing general outbound HTTP capabilities to frontend webviews that render hostile HTML.

#### 2. `fs:scope` limited to `$APPDATA` breaks attachment saving and `.eml` export at runtime
- **Severity**: HIGH
- **File**: `src-tauri/capabilities/content.json`
- **Exact Code**:
  ```json
    {
      "identifier": "fs:scope",
      "allow": [
        { "path": "$APPDATA" },
        { "path": "$APPDATA/**" }
      ]
    }
  ```
- **Why it is wrong**:
  The PR notes state that `dialog:default` and `fs:allow-write-file` are retained in `content.json` specifically for "attachment save" (and `ActionBar.tsx` provides "Export as .eml"). 
  When a user saves an attachment or exports an email from `ThreadView`, `dialog.save()` prompts the user to select a destination directory—typically `$DOWNLOAD`, `$DESKTOP`, or `$DOCUMENT`. When the frontend subsequently calls `writeFile()` via `@tauri-apps/plugin-fs`, Tauri validates the destination path against `fs:scope`. Because `fs:scope` only permits paths within `$APPDATA`, **any file save operation targeting standard user directories will fail with a runtime permission denial**.
  Additionally, when a user attaches a file in `ComposerWindow`, if the file is read from the local filesystem via `plugin-fs` `readFile()`, it will likewise fail for any user document outside `$APPDATA`.
- **Concrete Fix**:
  Do not perform user-facing file saving or reading through direct frontend `plugin-fs` calls in untrusted content windows. Instead, route attachment saving and `.eml` export through dedicated app-level Tauri commands (`#[tauri::command]`) in Rust. App commands are not restricted by frontend `fs:scope` and can safely write the selected file after dialog confirmation. Once moved to Rust commands, remove `fs:allow-write-file` and remove `$APPDATA/**` write permissions from `content.json`.

#### 3. Pop-out detection uses mutable URL parameters instead of immutable window labels
- **Severity**: MEDIUM
- **File**: `src/utils/windowKind.ts` and `src/main.tsx`
- **Exact Code**:
  ```ts
  // src/utils/windowKind.ts
  export function windowKindFromSearch(search: string): WindowKind {
    const params = new URLSearchParams(search);
    if (params.has("thread") && params.has("account")) return "thread";
    if (params.has("compose")) return "compose";
    return "main";
  }

  export function isPopoutWindow(): boolean {
    return windowKindFromSearch(window.location.search) !== "main";
  }
  ```
  ```tsx
  // src/main.tsx
  const windowKind = windowKindFromSearch(window.location.search);

  function Root() {
    if (windowKind === "thread") return <ThreadWindow />;
    if (windowKind === "compose") return <ComposerWindow />;
    return <RouterProvider router={router} />;
  }
  ```
- **Why it is wrong**:
  Tauri enforces permissions based exclusively on the **window label** (`main`, `thread-*`, `compose-*`). Conversely, `windowKind.ts` determines window kind and pop-out state based entirely on `window.location.search`. This creates dangerous mismatches:
  1. If a window is spawned with label `thread-123` but query parameters are missing or malformed (e.g., `?thread=123` without `account`), `windowKindFromSearch` evaluates to `"main"`. `main.tsx` then attempts to mount `RouterProvider` (the full main application) inside a window restricted by `content.json`. The application will crash as soon as it attempts to call main-only plugins (`notification:*`, `autostart:*`, `updater:*`, `core:window:*`).
  2. In `main.tsx`, `const windowKind` is evaluated once at module evaluation time, whereas `isPopoutWindow()` in child components evaluates dynamically against `window.location.search`. If client-side navigation or `history.replaceState()` occurs, the router state and `isPopoutWindow()` diverge.
  3. If query parameters are stripped in a pop-out window, `isPopoutWindow()` returns `false`, restoring the "Open in new window" buttons. Clicking them triggers `new WebviewWindow(...)`, which crashes due to the lack of `core:webview:allow-create-webview-window`.
- **Concrete Fix**:
  Determine window identity using the immutable Tauri window label:
  ```ts
  import { getCurrentWebviewWindow } from "@tauri-apps/api/webviewWindow";

  export function getWindowKind(): WindowKind {
    const label = getCurrentWebviewWindow().label;
    if (label.startsWith("thread-")) return "thread";
    if (label.startsWith("compose-")) return "compose";
    return "main";
  }

  export function isPopoutWindow(): boolean {
    return getWindowKind() !== "main";
  }
  ```
  Use `window.location.search` solely for parameter extraction (`threadId`, `accountId`), not for window role or security gating.

#### 4. Stripping `core:window:allow-close` breaks in-app close in `ComposerWindow`
- **Severity**: MEDIUM
- **File**: `src-tauri/capabilities/content.json` & `src/components/composer/Composer.tsx`
- **Exact Code**:
  ```json
  // src-tauri/capabilities/content.json:
  // "core:window:allow-close" omitted from content.json
  ```
  ```tsx
  // src/components/composer/Composer.tsx:
  <button
    onClick={closeComposer}
    className="text-text-tertiary hover:text-text-primary text-lg leading-none p-1"
    title="Close"
  >
    ×
  </button>
  ```
- **Why it is wrong**:
  The PR removed all window management permissions from `content.json`, asserting in `capabilities.test.ts` that:
  `"core:window:allow-close", // TitleBar is main-only; pop-outs have native decorations`.
  However, in `Composer.tsx` line 520, the composer renders an in-app "Close" (`×`) button. When `Composer` is rendered in a pop-out window (`ComposerWindow`), closing the composer requires closing the window itself. If `closeComposer` calls `getCurrentWindow().close()`, it will fail at runtime with a permission denied error. If it only resets local React state without closing the window, it leaves an orphaned, empty window open on the desktop.
  Allowing a window to close itself via `core:window:allow-close` is standard and does not represent an elevation of privilege.
- **Concrete Fix**:
  Add `"core:window:allow-close"` to `content.json` so pop-out windows can close themselves via in-app UI buttons and keyboard shortcuts.

#### 5. Tests enforce identical HTTP permissions instead of validating least privilege
- **Severity**: MEDIUM
- **File**: `src/config/capabilities.test.ts`
- **Exact Code**:
  ```ts
  describe.each(["main.json", "content.json"])("%s — http scope", (file) => {
    const capability = load(file);
    const http = capability.permissions.find(
      (p): p is { identifier: string; allow: { url: string }[] } =>
        typeof p === "object" && p.identifier === "http:default",
    );
    // Runs identical positive/negative URL checks on both files
  ```
  ```ts
  it("gives content windows a strict subset of main's grant", () => {
    const mainIds = new Set(main.permissions.map(idOf));
    for (const p of content.permissions) {
      expect(mainIds.has(idOf(p)), `${idOf(p)} is in content but not in main`).toBe(true);
    }
    expect(content.permissions.length).toBeLessThan(main.permissions.length);
  });
  ```
- **Why it is wrong**:
  1. The test suite actively mandates that `content.json` has the exact same over-permissive HTTP allowlist as `main.json`. Any attempt to fix Finding 1 by restricting `content.json` causes this test to go red. The test enshrines an insecure configuration rather than testing security requirements.
  2. While `main.json` has a literal snapshot assertion (`MAIN_PERMISSIONS`), `content.json` does not. A developer could add sensitive permissions from `main` (e.g. `core:window:default`, `dialog:allow-save`) or broaden permission scopes in `content.json` without failing the test, provided the permission is present in `main` and not in `FORBIDDEN_IN_CONTENT`.
- **Concrete Fix**:
  Decouple the HTTP scope tests between `main.json` and `content.json`. Define a dedicated `CONTENT_PERMISSIONS` snapshot in `capabilities.test.ts` and assert `expect(content.permissions).toEqual(CONTENT_PERMISSIONS);` to catch any accidental widening or modification of `content.json`.

#### 6. Pop-out handlers remain exposed to keyboard shortcuts and programmatic invocation
- **Severity**: LOW
- **File**: `src/components/email/ThreadView.tsx` & `src/components/composer/Composer.tsx`
- **Exact Code**:
  ```tsx
  // src/components/email/ThreadView.tsx
  onPopOut={isPopoutWindow() ? undefined : () => handlePopOut(thread)}
  ```
  ```tsx
  // src/components/composer/Composer.tsx
  {!isPopoutWindow() && (
    <button
      onClick={handlePopOutComposer}
      className="text-text-tertiary hover:text-text-primary p-1 rounded transition-colors"
      title="Open in new window"
    >
      <ExternalLink size={14} />
    </button>
  )}
  ```
- **Why it is wrong**:
  The PR only hides the pop-out buttons in the UI, but leaves the underlying action handlers (`handlePopOut`, `handlePopOutComposer`) active. If either component registers keyboard shortcuts (e.g., in a keymap hook or action handler) that call these functions, the handler will still invoke `new WebviewWindow(...)`. Because `core:webview:allow-create-webview-window` was removed from `content.json`, this results in an unhandled runtime exception.
- **Concrete Fix**:
  Add defensive guards directly inside `handlePopOut` and `handlePopOutComposer`:
  ```ts
  const handlePopOut = (thread: Thread) => {
    if (isPopoutWindow()) return;
    // ...
  };
  ```

#### 7. Over-permissive `opener:default` includes `reveal-item-in-dir`
- **Severity**: NIT
- **File**: `src-tauri/capabilities/content.json`
- **Exact Code**:
  ```json
  "opener:default",
  ```
- **Why it is wrong**:
  `opener:default` grants both `opener:allow-open-url` and `opener:allow-reveal-item-in-dir`. Pop-out email windows only need to open external hyperlinks in the default web browser. Exposing `reveal-item-in-dir` provides unnecessary filesystem reveal capabilities to windows rendering untrusted content.
- **Concrete Fix**:
  Replace `"opener:default"` with `"opener:allow-open-url"` in `content.json` and restrict allowed schemes to `https` and `http`.
