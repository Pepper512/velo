Crucially, the production implementation of `createMessageCache`, `threadMessageCache`, LRU capacity enforcement (REQ-2.2), `velo-sync-done` subscription (REQ-2.2), and `prefetch` cannot be inspected or verified in this review.

[H] F-02 — src/components/email/ThreadView.tsx — REQ-2.1 mandates rendering cached messages on the first paint with no skeleton, but lines 108–115 execute `threadMessageCache.peek()` and `setMessages(cached)` inside `useEffect`. Furthermore, `ThreadView` remains mounted across thread selections (`ReadingPane.tsx:19-21` does not key `<ThreadView/>`, relying on code outside the diff as described in the brief); changing `thread.id` via `j`/`k` leaves `messages` holding the previous thread's data and `loading: false` during the render phase, causing the first paint to flash the previous thread's messages under the new thread header before the effect runs.

[M] F-03 — src/components/layout/EmailList.tsx — Lines 273–287 place `visibleThreads` directly in the `useEffect` dependency array. `visibleThreads` reference changes on every page reload (e.g. debounced reloads following `velo-sync-done`), upon scroll pagination, and whenever thread store metadata (such as read or starred status) updates. Whenever `visibleThreads` receives a new array reference—even if `selectedThreadId` and its adjacent neighbour IDs have not changed—the cleanup at lines 283–286 cancels any in-flight prefetch `job` and restarts the 150 ms debounce timer. This thrashes and aborts prefetch queries prematurely whenever background sync or local status updates occur.

[M] F-04 — src/services/threads/messageCache.test.ts — REQ-2.2 specifies that the cache shall be cleared on `velo-sync-done`, and the task plan in the brief explicitly calls for "clear-on-sync" test coverage. Lines 58–64 test manual `cache.clear()`, but `messageCache.test.ts` contains no test for the `velo-sync-done` event listener, no test verifying the default capacity is 30, and no test exercising the exported `threadMessageCache` singleton. In conjunction with `messageCache.ts` being an opaque binary file in this commit, cache invalidation on sync is unverified.

[L] F-05 — src/services/threads/neighbours.ts — Line 21 accesses `visibleIds[at - i]` without checking `at - i >= 0`. When `selectedId` is the first element in the list (`at === 0`), `at - 1 === -1`, evaluating to `visibleIds[-1]`. While array property access with negative indices returns `undefined` in JavaScript and passes the `id !== undefined` guard on line 22, relying on negative index property lookup is unidiomatic and brittle compared to an explicit lower-bound check (`at - i >= 0`).

[L] F-06 — src/components/email/ThreadView.tsx — In line 120, `setMessages((prev) => (cached && sameMessages(prev, fresh) ? prev : fresh))` compares `fresh` against `prev`. While returning `prev` preserves reference equality for React re-render bailouts, `prev` could still be the prior thread's messages if state batching has not completed, or `[]` if not yet set. Comparing `sameMessages(cached, fresh)` directly against the snapshot peeked at effect start would be cleaner and deterministic.
